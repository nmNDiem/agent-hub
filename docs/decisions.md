# Decision register

Load this register only when a durable design question is not already settled by the active phase and domain packet. Current behavior belongs in domain/technical documents; sequencing belongs in [`roadmap.md`](roadmap.md).

## Confirmed decisions

| Area | Decision | Rationale | Consequence | Revisit trigger |
|---|---|---|---|---|
| Product | AgentHub is a general-purpose AI Agent platform; fashion Commerce is the first substantial domain capability. | Portfolio, Commerce and internal-assistant scenarios share the same platform concerns. | Core documentation and new core code must not assume a catalog. | Owner changes the product definition. |
| Workspace | Workspace is a generic tenancy/isolation boundary, not a shop or permanent business type. | Capability needs change over time and workspaces may be non-commercial. | No required Commerce records or permanent type discriminator. Historical shop wording may remain where harmless. | A concrete requirement needs mutually exclusive tenant behavior that capabilities cannot express simply. |
| Agent | Use one generic Agent aggregate; behavior derives from configuration, Knowledge, authorized Tools, policies, Channels and immutable revisions. | Avoids duplicated platform lifecycle and runtime logic. | Do not add `sales_agents`, `portfolio_agents` or similar foundational models by default. | A concrete domain proves a genuinely different aggregate lifecycle/invariant. |
| Domain ownership | Each domain owns its authoritative data and mutations. | Agents and Channels must not become alternate systems of record. | Agent configuration/Qdrant never duplicate current catalog, inventory, order or payment truth. | Never; only ownership may be deliberately reassigned by an approved migration. |
| Agent actions | Long-term execution is `Agent -> authorized typed Tool/Action -> Domain Service -> domain state`. | Keeps model output untrusted and business rules enforceable. | Workspace scope is server-injected; services reauthorize; high-impact actions may require approval. | The first effectful tool triggers the minimal authorization/audit implementation. |
| Action abstraction | Build a complete real workflow before extracting shared action, integration or automation infrastructure. | Reuse cannot be validated before concrete workflows expose genuinely repeated constraints. | The first implementation stays as small as its workflow permits; extract only proven repetition from later action families. | Two or more implemented workflows demonstrate the same stable contract and lifecycle. |
| Tool infrastructure | Do not build a speculative plugin framework, universal registry, service locator or workflow engine. | No current second implementation justifies the complexity. | Add only the smallest composition boundary required by an approved tool use case. | A concrete second/third tool family demonstrates repeated integration needs. |
| Workflow language | Roadmap and product UI describe user outcomes rather than Forms, Documents, Calendar APIs, webhooks or tool schemas. | Users need to understand what an Agent can accomplish, not assemble developer primitives. | Supporting components do not automatically become peer domains, phases or top-level navigation. | A component proves an independent authoritative lifecycle and operator workflow that warrants domain ownership. |
| Knowledge | PostgreSQL owns Knowledge sources, versions, chunks and active generations; Qdrant is derived/rebuildable. | Deletion, tenancy and lifecycle require relational authority. | Vector hits are filtered and revalidated; structured mutable facts stay outside RAG. | A replacement must preserve equivalent authority and rebuild semantics. |
| Runtime provider | OpenAI remains behind server-side generation, vision and embedding adapters. | This is the approved implemented stack. | No extra model provider without an approved task-specific reason. | Reliability, capability, legal or commercial evidence justifies another provider. |
| Architecture | Use a domain-oriented modular monolith and `router/adapter -> service -> repository/provider`. | Current scale benefits from local transactions and lower operational complexity. | No microservice split, Redis or distributed workflow framework by default. | Measured scaling, isolation or deployment requirements exceed the monolith. |
| Commerce priority | Commerce is optional per workspace but is a major planned AgentHub product track. | Portfolio and internal-assistant workspaces must remain viable while AgentHub develops substantial retail/business operations. | Commerce is not a prerequisite for non-Commerce Agents; roadmap and phase planning must still treat it as committed product direction rather than a vague possibility. | Owner changes the product strategy. |
| Commerce compatibility | Current Commerce functionality is preserved and extended additively. | Implemented product depth should not be disrupted for conceptual purity. | Do not rename or rehome working modules without a functional reason and bounded migration. | A functional blocker requires a bounded migration. |
| Inventory | Current quantity is sufficient for read availability; operational mutation requires a transactional service and auditable stock movements. | POS, returns and transfers need proof of why stock changed. | No POS/order fulfillment/return mutation may write levels as an unaudited number. | First approved operational stock mutation. |
| POS truth | POS reuses the authoritative Orders and Inventory domains. | Checkout is a sales interface, not an independent transaction system. | POS may add cart, barcode, cashier/session and location workflows but cannot create parallel order or stock truth. | A separately approved architecture decision deliberately reassigns domain ownership. |
| Contact/customer | Contact is a generic cross-channel identity/relationship; it is not automatically a Commerce Customer. | Non-commerce conversations also produce contacts. | Future Commerce customer profile may link to Contact through an explicit domain decision. | Commerce customer lifecycle is approved. |
| Payments/custody | AgentHub records and orchestrates provider-backed payments but does not default to custody of customer or merchant funds. | Payment workflows need operational truth without casually entering custody or intermediary scope. | Store minimum payment references/status, verify events and reconcile Orders; wallets, custody and unlicensed intermediation require separate approval. | Separate owner-approved product, legal, security and architecture review. |
| Regulated capabilities | Regulated capabilities are integration-first unless separately approved. | Qualified providers can own regulated execution while AgentHub owns bounded orchestration and operational records. | Payments, e-invoicing, digital signatures/trust services, regulated accounting services and banking/credit integrations load [`compliance.md`](compliance.md). | A direct service is explicitly approved after legal, product, security and architecture review. |
| Accounting boundary | Accounting/reporting software is distinct from providing regulated accounting services. | Software calculations and records do not automatically authorize professional representation or certification. | AgentHub may own software workflows; regulated service provision requires a qualified provider or separate approval. | Approved service model changes AgentHub's role. |
| Trust-service boundary | Electronic-signature integration is distinct from operating a trust service or certificate authority. | Integrating qualified signing is materially different from issuing credentials or regulated trust services. | Prefer provider integration; direct trust-service/CA operation requires separate approval. | Approved service model changes AgentHub's role. |
| Marketplace compliance | Marketplace or e-commerce-platform functionality requires a separate compliance review. | Multi-merchant/platform operation can create obligations beyond a workspace's own Commerce operations. | Identify operator, merchant, payment, consumer, tax, data and registration/notification responsibilities before approval. | A phase proposes marketplace/platform behavior. |
| AI and personal data | AI and personal-data compliance are cross-cutting platform concerns. | Risk follows use case and data flow rather than a single module. | Sensitive AI uses and material personal-data changes trigger scoped review under [`compliance.md`](compliance.md); ordinary work does not preload it. | Applicable law, market, use case or processing materially changes. |
| Agent workspace | The primary experience is Agent-centric: World overview plus focused configure/test/publish/operate screens and contextual navigation. | A generic sidebar/table CMS obscures Agent identity, relationships, activity and handover. | The World is a projection of real state and keeps an accessible conventional path; phase 3.2 establishes the interaction language without rewriting every screen. | User research or an approved product-direction change proves a different interaction model. |
| Compatibility | Preserve working APIs, identifiers, routes and schema unless a concrete requirement authorizes change. | Migration cost and risk outweigh cosmetic consistency. | Historical internal routes such as `/create-shop` may remain naming debt, while approved user-facing experiences use generic Workspace/Agent language where current wording misleads users. | The identifier causes a functional/security blocker or a bounded migration is approved. |
| UI | UI represents user tasks and meaningful relationships, not the database schema. | A table-per-navigation CMS obscures agent operation. | Use progressive disclosure and contextual domain UI; avoid filler and duplicate facts. | User research or a concrete workflow proves a different information architecture. |

## Confirmed technology and data choices

- Next.js/strict TypeScript dashboard and independent TypeScript/Vite widget.
- FastAPI/Python 3.12 backend with SQLAlchemy async and Alembic.
- Supabase PostgreSQL and private Storage; Supabase Vault for channel credentials.
- FastAPI-owned email/password authentication, not Supabase Auth.
- UUIDv7 and BIGINT usage as specified in [`data-model.md`](data-model.md).
- Typed bounded custom orchestration rather than an agent framework.
- Durable PostgreSQL jobs with leases/fencing for ingestion and outbound work.
- Current Catalog truth uses exact Decimal prices, generic options, locations and nullable inventory where `NULL` differs from zero.

## Open operating choices

These do not reopen product architecture:

- exact production model IDs, embedding dimensions and budgets;
- production retention periods and jurisdiction-specific privacy wording;
- Zalo/provider prerequisites and supported provider-specific message classes;
- production domains, backup objectives and external connector vendors;
- commercial plan structure and payment provider for platform billing.

Owner instructions may supersede a decision. Update this register, affected authority documents and the approved task together; do not silently reinterpret an open implementation choice as permission to change the product or stack.
