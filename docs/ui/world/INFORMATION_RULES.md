# AgentHub World — Information Rules

These rules are mandatory.

## 1. One screen, one primary question

Every projection or focused view must have one explicit primary question.

Examples:

- System: how is the workspace connected?
- Agents: how do agent scopes differ?
- Catalog: how do catalog scope, collections and locations relate?
- Customers: where is runtime activity flowing?

If information does not help answer the current primary question, it should usually not be visible.

---

## 2. One fact, one visual owner

The same fact must not be repeated across canvas, toolbar, sidebar and inspector on the same screen.

Bad:

```text
Canvas: Sales Agent — 184 conversations
Inspector heading: 184 active conversations
Toolbar: Conversations 184
```

Good:

```text
Canvas owns total activity: 184 active
Inspector owns decomposition: AI 132 / Human 21 / Waiting 28 / Failed 3
```

A child/detail value is not considered duplication when it explains the parent aggregate.

---

## 3. Progressive disclosure

Information appears in this order:

```text
Orientation
-> Structure
-> State
-> Detail
-> Action
```

Do not expose detail before structure is understood.

---

## 4. No data exhaust

The presence of a metric in the backend is not sufficient reason to show it.

Do not automatically surface:

- token counts
- chunk counts
- timestamps
- IDs
- every status enum
- every count
- every historical event
- every provider detail

Each visible fact needs a user-facing purpose.

---

## 5. Normal state is quiet

Healthy state should consume minimal attention.

Do not repeat:

```text
Healthy
Connected
Active
Online
```

on every object simultaneously.

Use visual silence for normal state and stronger signaling for exceptions.

---

## 6. Aggregate before expanding

Large collections must be aggregated until the user explicitly asks for detail.

Examples:

```text
184 active conversations
```

not 184 nodes.

```text
3 knowledge sources
```

not 428 chunk nodes.

```text
Women collection
```

not every product and variant.

---

## 7. Relationship budget

An edge exists only when the relationship is important to the current question.

Do not turn the canvas into an entity relationship diagram.

Before rendering an edge, ask:

> Would the user misunderstand the system without seeing this relationship now?

If no, hide it until a more specific context.

---

## 8. No decorative duplication

Do not show a count in both:

- node label and badge
- title and subtitle
- canvas and nearby legend
- inspector header and first section

Do not add summary cards above a visualization that already communicates the same summary.

---

## 9. Legends are earned

A legend is allowed only when visual semantics cannot be understood without it.

Prefer stable visual grammar over permanent legends.

Do not add a legend simply because multiple colors exist.

---

## 10. Filters must change the model, not merely highlight it

A filter or projection control should materially reduce or reorganize what is shown.

Do not create controls that only recolor the same cluttered graph.

---

## 11. Inspector content is contextual

Inspector sections are generated by selected object type and available meaningful detail.

Do not preserve empty template sections.

For example, a Channel inspector should not contain placeholder Catalog sections.

---

## 12. Every element must pass the three-question test

Before adding any visible UI element, answer:

1. What user question does it answer?
2. Is the same information already visible elsewhere on this screen?
3. Would removing it prevent understanding or action?

Rules:

- if #1 has no clear answer -> remove it
- if #2 is yes -> remove one owner
- if #3 is no -> strongly prefer removal

This rule applies to:

- labels
- metrics
- cards
- icons
- buttons
- badges
- animations
- dividers
- legends
- tooltips
- edges

---

## 13. No professional-looking filler

Never add UI because it makes the product look more complete or enterprise-like.

Forbidden examples:

- decorative KPI strip
- arbitrary “recent activity” panel on every inspector
- extra tabs with sparse content
- badges for every state
- redundant mini charts
- fake utilization metrics
- generic “Overview” section with repeated facts

The interface should feel intentionally sparse when the task is simple.

---

## 14. Information ownership table

Initial ownership for the first prototype:

| Information | Primary owner |
|---|---|
| Agent identity | Agent node |
| Agent exceptional state | Agent node |
| Connected channel identity | Channel node / structural edge |
| Assigned knowledge identity | Knowledge node |
| Catalog scope relationship | Catalog branch |
| Total active runtime activity | Agent activity aggregate |
| Runtime state breakdown | Inspector when agent selected |
| Detailed records | Dedicated screen or inspector drill-down |
| Configuration actions | Inspector / settings surface |
| Global projection | World projection control |

If implementation needs a new fact, explicitly assign its owner before rendering it.
