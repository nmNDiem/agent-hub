# M1.1 Shared channel foundation

## Goal

Create the tenant-safe channel and conversation foundation that Website, Facebook Messenger
and Zalo can share, while preserving all existing Website API, SSE, quota, image, lead and
retention behavior.

## Acceptance criteria

- Channel connections, agent bindings and Website-specific presentation configuration have
  separate ownership and workspace-safe relationships.
- Conversations and messages are owned by the conversations domain and retain channel
  provenance, explicit direction, lifecycle, workflow status and `ai | human | paused`
  handling mode.
- Verified inbound events are persisted and deduplicated before normalized messages or paid
  model work can be created.
- Provider thread and message identifiers are opaque and unique only within their connection.
- Outbound deliveries are persisted before provider calls and support idempotent claim,
  completion, bounded retry and terminal failure transitions.
- Typed, capability-aware adapter contracts isolate verification, normalization, rendering,
  delivery and safe provider error classification.
- Existing Website records are backfilled into the shared model without changing public IDs,
  routes, response schemas, SSE event order, transcript replay, quota, images, leads or
  retention behavior.
- Every newly exposed tenant-owned resource has a negative cross-workspace test.
- Duplicate and reordered inbound events cannot duplicate a conversation, message or model
  turn; an accepted outbound delivery cannot be sent again.

## Confirmed decisions

- FastAPI remains the only channel business API and the backend remains a modular monolith.
- Website, Facebook Messenger and Zalo share conversation state but keep transport-specific
  adapters.
- Widget origin/session authorization, image handling, rate limits and SSE remain in the
  Website transport boundary.
- Conversation lifecycle (`active | deleted`), workflow status
  (`open | pending | resolved`) and handling mode (`ai | human | paused`) are independent.
- Adapter responsibilities use small typed protocols; Website is not required to implement a
  webhook verifier or external delivery client.
- Channel rows store only an opaque credential reference. A `CredentialVault` contract is
  introduced, but real provider credential ingestion and the production vault backend belong
  to the provider tasks and must exist before any real token is accepted.
- No Facebook or Zalo route, SDK, credential, provider call or UI is introduced in this task.
- No continuous delivery worker is introduced; the durable delivery state machine and runner
  are executable with injected adapters and can be scheduled by later provider tasks.

## Data, API, UI and security impact

- Add channel connection, binding, Website configuration, webhook event, external mapping and
  outbound delivery tables through Alembic.
- Backfill existing Website channel and conversation data, including tenant-safe foreign keys,
  and provide a practical downgrade.
- Keep current public and dashboard HTTP/SSE contracts additive and behavior-compatible.
- Do not add or redesign a screen.
- Verify inbound authenticity before connection resolution at adapter boundaries; shared
  services accept only verified envelopes.
- Never persist raw webhook bodies, credentials, provider response bodies, message text in
  operational errors, or unbounded provider metadata.

## Test plan

- Unit-test normalized contracts, capability fallback, handling-mode decisions and delivery
  state transitions.
- Test duplicate/idempotency conflicts, reordered events, lease expiry, bounded retry,
  terminal failure and accepted-delivery replay protection with fake adapters.
- Test identical external IDs on different connections and negative cross-workspace access.
- Run existing Website public, conversation, lead, usage and retention regressions.
- Run Ruff, strict mypy, pytest, Alembic offline upgrade SQL and practical migration
  upgrade/downgrade checks where the configured environment permits them.
- Do not invoke paid OpenAI, Facebook or Zalo flows.

## Documentation impact

Update the authoritative channel, conversation, architecture, data-model and testing documents
for implemented behavior. Remove this active task file after completion; Git retains the
approved specification.

## Out of scope

- Facebook Messenger and Zalo connection APIs, webhooks, signatures, payload support and SDKs.
- A production credential vault or key-management choice.
- Unified inbox UI, human reply endpoints, assignment, unread state, notes and tags.
- Contact identity linking/merge and social media download/storage pipelines.
- Production worker deployment and provider-specific message-window or opt-out policy.
