# M1.2 Facebook outbound text and delivery receipts

## Goal

Complete the official Facebook text transport loop for already-normalized outbound messages:
durable Graph API delivery, accurate acceptance versus delivery state, and authenticated delivery
receipts. This establishes the reusable outbound pattern before Zalo begins.

## Acceptance criteria

- A normalized Facebook outbound message is queued once and delivered by the existing leased,
  fenced, bounded-retry channel pipeline.
- The adapter resolves the Page token from the credential vault and sends text with
  `messaging_type=RESPONSE` to the connection-scoped PSID through the configured Graph version.
- Graph acceptance persists the provider message ID as `accepted`; it is not mislabeled as
  end-user delivery.
- Authenticated `delivery.mids` webhook events move matching accepted deliveries to `delivered`.
- Duplicate receipts are idempotent, and a receipt that arrives before Graph acceptance is
  retained and reconciled after the provider message ID is persisted.
- Revoked/missing credentials and provider failures use safe terminal/retryable classifications;
  tokens, message text and raw provider errors are never logged or returned.
- Cross-workspace/provider IDs cannot update another tenant's delivery.
- A dedicated channel worker entry point runs fake adapters in tests and never invokes live Meta
  automatically.

## Confirmed decisions

- Official HTTPS Graph API only; no MQTT or reverse-engineered client session.
- Add `accepted` between `sending` and `delivered` because the Send API response proves provider
  acceptance, while delivery webhooks prove delivery.
- Persist minimal delivery-receipt identity rather than raw webhook bodies so reordered receipts
  cannot be lost.
- The worker is separate from the knowledge worker and reuses the M1.1 lease/fencing service.
- Treat a timeout, transport disconnect or HTTP 5xx after a send attempt as terminal
  `FACEBOOK_DELIVERY_UNKNOWN`. Without a verified provider idempotency contract, automatically
  retrying an ambiguous request could send a duplicate customer reply. Explicit rate-limit and
  pre-acceptance transient rejections remain bounded-retryable.

## Data, API, UI and security impact

- Add Alembic `0015` for the `accepted` delivery state, acceptance/delivery timestamps and a
  tenant-scoped receipt table.
- Extend the existing signed Facebook webhook; no new public webhook route.
- Add no dashboard route or UI. Operator delivery presentation remains M1.4.
- Vault credentials are resolved only inside the server-side outbound adapter.

## Test plan

- Migration upgrade/backfill/downgrade test on PostgreSQL.
- Graph request/response and safe error-classification tests with `httpx` mock transport.
- Queue, lease, retry, terminal failure, duplicate/reordered receipt and stale-fence tests.
- Negative cross-workspace and revoked/missing credential tests.
- Full Ruff, mypy, pytest and offline Alembic checks; no paid/provider flow.

## Documentation impact

- Update channels, API, data model, operations and testing documents once behavior is verified.

## Out of scope

- Creating AI responses from inbound messages.
- Attachments, templates, reactions, read receipts or sender actions.
- Message-window/opt-out policy and reauthorization UX.
- Inbox UI or public/manual send API.
