## F3 ordered implementation slices

F3 remains one authoritative roadmap phase and one release gate. Implement it as the following ordered, reviewable slices; a completed slice does not by itself mark F3 complete or authorize F4 work.

| Slice | Scope | Slice acceptance criteria |
|---|---|---|
| F3.1 agent foundation and catalog tools | Agent/config persistence, location/collection assignments, immutable allowed catalog scope and typed tools over `CatalogReadService`; no LLM call is required | Cross-workspace access is denied; query intent can only narrow authorized scope; tools preserve same-variant option semantics and authoritative effective price/inventory |
| F3.2 knowledge persistence and ingestion | Shop profile/FAQ, knowledge bases and agent links, documents, chunks, ingestion jobs, immutable embedding-profile metadata, PDF/TXT extraction, chunking and retry/idempotency boundaries | Invalid or untrusted files fail safely; authoritative state remains in Postgres; unit tests use fake embedding/vector adapters and cover tenant isolation |
| F3.3 embedding and Qdrant retrieval | OpenAI `EmbeddingProvider`, Qdrant `KnowledgeVectorIndex`, post-transactional indexing, rebuild/re-index flow, server-injected filters and Postgres result revalidation | Real non-production Qdrant integration proves cross-workspace isolation; stale/revoked generations cannot be retrieved; batching, citation references and failure behavior are covered |
| F3.4 grounded agent runtime | OpenAI generation adapter, simple orchestration across retrieval and catalog tools, normalized product-card output, prompt-injection defenses and usage bounds | Answers do not fabricate SKU, price, stock, discounts or commitments; generic schemas and unknown inventory work; prompt-injection, cost/token/tool-call and safe-error regressions pass |
| F3.5 dashboard knowledge UI and Playground | Knowledge upload/status/error UI, agent configuration UI and authenticated Playground SSE with stop/loading/error, grounded sources and schema-neutral product cards | Integrated dashboard flow is usable and accessible; SSE cancellation/errors are handled; source and product-card rendering works for product-only and multi-option fixtures |

The F3 release gate in [`../22-phase-gates.md`](../22-phase-gates.md) closes only after F3.1 through F3.5 pass together. F3.2 must remain testable without external providers; F3.3 is the separately verifiable OpenAI/Qdrant integration boundary defined by [ADR-0002](adr/0002-qdrant-embedding-providers.md).

## Implementation status

- F0 scaffold: completed.
- F1 identity/tenants: implemented locally with Argon2id credentials, HttpOnly access/refresh cookies, rotating refresh-token families, CSRF/origin checks, workspace membership enforcement, onboarding and tenant-negative tests. The implementation is organized as `identity` and `workspaces` domain modules; services own transactions and repositories do not commit. Dashboard auth/workspace UI lives under `src/features/`.
- Email verification and recovery routes are registered only when `EMAIL_DELIVERY_ENABLED=true`; a real delivery provider remains required before enabling them outside tests.
- F2 fashion catalog: implemented locally with workspace-scoped product/variant/optional size-guide CRUD, exact Decimal pricing, nullable stock, archived SKU reservation, stable cursor pagination, private image upload/signed URLs with retryable cleanup state, transactional CSV preview/import idempotency, and a responsive catalog dashboard. Supabase Storage credentials and a private bucket are required for real image operations; automated tests use a fake adapter.
- F2.1 universal catalog: complete with generic catalog relations, legacy color/size compatibility, CSV/XLS/XLSX extraction, persisted staging/issues/mapping profiles, diff, atomic idempotent MERGE, structured same-variant option search and a responsive import wizard. Critical real-PostgreSQL migration, JSONB, uniqueness, transaction and tenant-scope checks passed in the isolated `agenthub_test` schema.
- F2.2 location catalog scope: complete with generic locations, `(location_id, variant_id)` inventory, optional location price overrides, reusable collections, workspace/location/collection-scoped search, explicit location-code imports and dashboard management. The real-PostgreSQL default-location/implicit-variant/stock backfill gate passed. Agent assignments were deliberately deferred to F3.
- F3.1 agent foundation and catalog tools: complete with workspace-owned agent configuration, UUIDv7 public IDs, explicit all/selected location and collection scope, composite tenant-safe assignments, immutable scope resolution and internal typed `search_products`, `get_product_detail` and `check_stock` tools. Managed image paths remain private, generic options are authoritative, and no LLM/provider call or publish flow is part of this slice.
- F3.2 knowledge persistence and ingestion: complete with tenant-scoped knowledge bases/agent assignments, immutable document versions and generations, private streaming PDF/TXT upload, explicit quotas, idempotent jobs, fenced leases/heartbeat, sandboxed strict PDF parsing, deterministic chunks/vector point identities, classified retries, atomic active-generation rules and orphan reconciliation. This slice deliberately left concrete adapters, profile backfill/promotion and retrieval to F3.3; it did not guess or seed a model/profile.
- F3.3 embedding and Qdrant retrieval: complete with a concrete OpenAI embedding adapter, Qdrant Cloud vector-index adapter, server-injected workspace/source filters, Postgres active-generation revalidation, real citations, classified provider failures, idempotent rebuild, initial-profile activation and target-profile backfill/promotion. The real non-production Qdrant gate passed with identical cross-tenant vectors, stale-generation rejection and idempotent upsert/delete. No paid OpenAI request was made and no embedding profile is seeded until the operator explicitly configures a verified model and dimensions.
- F3.4 grounded agent runtime: complete with a provider-neutral generation boundary, concrete OpenAI tool-call adapter, deterministic bounded orchestration over tenant-scoped retrieval/catalog tools, server-built schema-neutral product cards, validated evidence references, explicit unknown inventory and prompt-grounded natural responses. Agent personality is editable and locale-aware defaults make new chatbots immediately testable. Output is no longer rejected by subjective keyword lists; structural references, tenant scope, schemas and budgets remain server-enforced, and recoverable malformed calls receive bounded correction feedback. Offline tests use fake generation. A bounded live compatibility check on 2026-10-01 confirmed that the operator-configured `gpt-6-luna` can issue the required Chat Completions function call with `reasoning_effort="none"`. Playground/SSE is integrated by F3.5 below.
- F3.5 dashboard knowledge UI and Playground: implemented locally with responsive role-aware knowledge management, PDF/TXT and manual ingestion controls, real job states/retry/delete, and one unified chatbot workbench for draft/catalog/knowledge configuration plus authenticated SSE testing. The former standalone Playground route redirects to the selected chatbot in this workbench. Playground history is bounded and local-only; Stop aborts the request while retaining partial output, validated source references plus schema-neutral product cards render without invented images or values, and exhausted runtime recovery becomes a neutral conversational reply instead of exposing internal codes. The admin shell offers the accessible Aurora, Lagoon and Ember palettes, defaults to Lagoon, and persists the allowlisted choice in browser storage without environment configuration or backend state. Automated fixtures cover palette persistence, legacy redirect, product-only and multi-option records, SSE chunk boundaries, conversational fallbacks and cross-workspace denial. The broader F3 release gate still requires an operator-configured end-to-end Playground/provider check; the F3.4 adapter compatibility request does not close that integrated gate.
- The F3 catalog boundary is now explicit: authorization produces an immutable allowed workspace/location/collection scope, query intent may only narrow it, and `CatalogReadService` returns product-centric variants plus price/availability summaries. Location and collection sets use union within each set and intersection across the two sets. Candidate products are limited before batched hydration; option loading does not issue queries per variant.
- When no location is selected, price is exact/range/unknown and availability is counted by in-stock/out-of-stock/unknown state; quantities are never summed across locations. Per-location reads include effective price and inventory freshness. The existing dashboard route keeps singular `location_id`/`collection_id`; F3 tools consume the typed domain read models and F4 later maps them to a separate public product-card DTO.
- F3 must consume this catalog read contract rather than recreate filtering or depend on legacy color/size columns. F4 consumes the normalized F3 product-card output and must support products without variants, options or size guides.
- PostgreSQL integration tests are opt-in and recreate only `agenthub_test` in the database named by `DATABASE_URL`, with local/test environment guards and cleanup. MVP coverage targets critical database flows; broader coverage is deferred to pre-release hardening.
