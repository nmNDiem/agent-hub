# ADR F3.3 — OpenAI embeddings and Qdrant retrieval boundary

Status: Accepted (2026-09-30).

## Context

F3.2 persisted authoritative sources, generations, chunks, embedding mappings and durable jobs without selecting a live embedding profile. F3.3 must connect that state to OpenAI embeddings and the owner-selected non-production Qdrant Cloud runtime without making Qdrant authoritative, leaking tenants or requiring a paid OpenAI call in automated tests.

## Decision

- `OpenAIEmbeddingProvider` is the only concrete embedding provider. It sends an explicitly configured model and dimension, batches inputs, validates returned count/dimensions and disables SDK retries so the PostgreSQL job retry budget remains authoritative.
- Temporary network, timeout, rate-limit and server failures are retryable. Invalid authentication, input, model/dimension or exhausted credit are permanent configuration failures. Errors and logs never contain source text or credentials.
- `QdrantKnowledgeVectorIndex` uses one collection per immutable embedding profile, shared across workspaces. The `workspace_id` payload index is marked as a tenant field; knowledge-base and profile payload indexes support mandatory filtering.
- Every vector query injects the validated workspace, allowed knowledge-base IDs and embedding profile. Returned point IDs and payload identities are batch-revalidated against indexed mappings, matching content hashes, active/ready generations, active documents/bases and the base's active profile in PostgreSQL.
- Retrieval returns content plus real document/chunk citations only after revalidation. If embedding or Qdrant is unavailable, retrieval raises an explicit unavailable result rather than returning stale or partially scoped context.
- Scores from different profiles are never compared directly. Results from multiple active profiles are merged deterministically by per-profile rank.
- The operator workflow creates a profile/collection from explicit environment configuration, activates initially unprofiled bases, queues idempotent rebuilds, backfills a target profile and atomically promotes it only after every active document has a fully indexed ready generation. Previous generations remain ready for controlled rollback but fail active-profile/generation revalidation after cutover.
- The knowledge worker remains a process separate from FastAPI. Qdrant cleanup is retried after temporary outages without losing the authoritative `deleting` state.
- Development integration uses the owner-confirmed non-production Qdrant Cloud cluster. Each test creates one random collection containing `_test_`, proves cross-workspace/source isolation, stale-generation rejection and idempotent upsert/delete, then deletes only that exact collection.
- Automated tests use deterministic fake embeddings. No OpenAI request or model profile is created until an operator explicitly supplies a verified model and dimensions.

## Consequences

- `OPENAI_API_KEY` is required only to run the real ingestion worker, not for offline tests or the Qdrant integration gate.
- `QDRANT_URL` and `QDRANT_API_KEY` remain server-only. Browser code never contacts Qdrant.
- A future embedding model/dimension change is a new immutable profile plus backfill and promotion, never an in-place edit.
- F3.3 does not implement answer generation, prompt construction, Playground SSE or widget behavior; those remain F3.4/F3.5.

## Verification

- Offline tests cover OpenAI batching/dimension checks, Qdrant filter construction, provider outage behavior, citation revalidation, negative cross-workspace access, stale generation rejection, initial profile activation, rebuild idempotency and atomic profile cutover.
- The opt-in Qdrant Cloud integration uses deterministic three-dimensional vectors and makes no OpenAI request.
