# 3.2 — Agent workspace experience

Status: **Approved for implementation**

## Goal

Establish AgentHub's Agent-centric interaction language: a user can understand a workspace as an operational system of Agents, Knowledge, Channels, Conversations, handover and enabled business systems, then move coherently through creating, configuring, testing, publishing and operating an Agent without being forced into a generic CMS or developer-tool mental model.

## User-visible outcome

An operator enters a workspace and sees an honest, navigable World of its Agents and meaningful relationships. The operator can select an Agent, understand who it is, what it knows, where it works, what it may do, its publish/operational state, current attention needs and how to continue configuring or operating it. Knowledge-only workspaces remain complete without Commerce, while Commerce-enabled workspaces retain equivalent access to current Catalog behavior.

## Existing Behavior to Preserve

- Authentication, workspace membership, CSRF and server-side tenant authorization remain unchanged.
- Agents retain current draft configuration, immutable published revisions, pause/archive behavior, Playground, Website publishing and Facebook/Zalo bindings.
- Knowledge assignment, freshness/version/recovery/diagnostic behavior remains owned by Knowledge.
- Website, Facebook and Zalo continue to converge on normalized Conversations, Contacts and explicit AI/human handover.
- Knowledge-only Agents require no Catalog data, Catalog navigation or Commerce setup and cannot produce product cards.
- Commerce-enabled Agents retain current Catalog location/collection scope, conditional read tools and validated product evidence.
- Current deep links and focused management screens remain reachable; the World cannot become the only way to navigate.
- Dashboard metrics, connection health, Agent state and activity remain real persisted facts. Empty stays empty.
- No current route, identifier, schema or public/widget contract is renamed merely to remove historical Commerce wording.

## Scope

### Agent-centric workspace and World

- Replace the generic KPI-first workspace entry with a coherent operational overview that can represent multiple Agents and the workspace systems around them.
- Show meaningful real relationships: Agent to assigned Knowledge, bound Channels, current Conversation activity/handover state and enabled domain access such as Catalog scope.
- Treat the World as a projection of authoritative backend state. It owns no business state and does not infer relationships from labels, layout or model output.
- Provide the System and Agents projections needed for the first coherent experience. Catalog appears only as a contextual relationship inside those projections when its real capability and data exist. A separate Catalog projection and a Commerce Customer projection are not part of this delivery; generic Contacts remain a focused screen.
- Use selection, focus, semantic zoom and one accessible inspector to reveal increasing detail without duplicating the same fact in cards, nodes and panels.
- Represent normal operation quietly and use motion/attention only for meaningful selection, activity, failure, disconnection or human-intervention state.

### Agent lifecycle and focused work

- Provide a coherent path through Create → Configure identity/instructions → assign Knowledge → configure current Channels and domain access → Test → Publish/deploy → Observe Conversations/activity → Improve.
- Preserve existing Agent workbench, Playground and channel panels as focused work, reorganizing or linking them where necessary instead of rewriting their behavior wholesale.
- Make draft, published, paused and archived/unavailable states understandable. Historical Conversations keep their revision identity.
- Present publish as selection of an immutable usable revision. Show only readiness facts that can be derived from real current requirements; distinguish blocking, optional, unavailable and forbidden states.
- Expose handover and human intervention through the existing Conversation state rather than a separate Agent-owned flag.

### Navigation and product language

- Make primary navigation contextual to the workspace and task. The overview response is the source for contextual navigation; the client does not infer capability availability from labels, local role checks or whether a request happened to fail.
- Treat Catalog as available when the server-authorized projection finds at least one active Catalog product, location or collection, or resolves an Agent Catalog assignment to an accessible record. When available, show Catalog, Locations and Collections according to the actor's existing authorization.
- When Catalog is not available, hide Catalog, Locations and Collections from primary navigation. If the actor is authorized to create Catalog data, expose one explicit **Set up Commerce** action from the overview or a secondary management surface so an empty Commerce setup is not a navigation dead end. Do not show that action to an actor without the existing management permission.
- Prefer Agent, Workspace, Knowledge, Conversations and user goals over “Chatbot”, “shop” and implementation primitives in user-visible copy where the phase touches the experience.
- Preserve compatible routes and direct access to current domain screens. Internal historical identifiers may remain until a bounded functional migration is justified.
- Describe abilities in user language. Do not expose Forms, Documents, tool schemas, function definitions or a capability registry as required mental models.

### Guidance, states and responsive operation

- Add useful empty states, next-step suggestions, inline explanations, validation, recoverable-error guidance and bounded capability discovery required to complete the current Agent lifecycle.
- Show loading, empty, ready, partial, stale, disconnected, degraded, failed, forbidden, draft, published, paused and needs-attention states where applicable.
- Preserve user input during recoverable focused-work errors and never make a partial projection look complete.
- Keep the World and focused workflows usable at 1440, 1024, 768, 390 and 320 pixels. Narrow layouts may switch to tabs or list-to-detail rather than shrink a desktop graph beyond usability.
- Provide keyboard navigation, visible focus, semantic DOM/structured alternatives, text in addition to color and reduced-motion behavior. The spatial view is not the sole accessibility path.

### Data access and integration

- Add one bounded authenticated `GET /api/v1/workspaces/{workspace_id}/overview` projection composed server-side from owning domains. The current dashboard and per-Agent contracts do not provide the required relationships as one authorized, consistent view and must not be fanned out per Agent by the client.
- Keep the existing dashboard endpoint compatible for focused analytics or legacy consumers; do not make the World assemble its initial state from that endpoint plus per-Agent requests.
- The projection may contain identifiers, relationship kinds, bounded counts, factual health/state and safe attention reasons. It does not copy private document bodies, Conversation transcripts, secrets or authoritative mutable state.
- All links and actions route back to the owning Agent, Knowledge, Channel, Conversation, Contact, Analytics or Commerce service.

## Non-goals

- A repository-wide frontend/backend rewrite, route rename, schema migration or new state architecture for conceptual purity.
- A generic action platform, plugin/capability registry, workflow engine, arbitrary-code tool or effectful Agent Action.
- New Orders, Booking, payment, Calendar, email, document-generation or Commerce operations.
- Evaluation suites, feedback triage, regression comparison, canary rollout or model observability owned by phase 6.1.
- Full end-to-end guided onboarding, workspace invitations, billing, plans or operator controls.
- Replacing Inbox, Knowledge, Agent configuration, Catalog or other deep operational screens with graph editing.
- A 3D game, decorative environment, card flipping/rotation, meaningless floating panels, generic AI-person imagery or motion without information.
- Fake Agents, fake activity, fake connected state, fake metrics or demo fixtures presented as product state.
- Canvas/WebGL, a force-directed layout or a new visualization dependency for this delivery.

## Confirmed Decisions

- The Agent is the primary interaction entity; the workspace overview represents multiple Agents and their real operational relationships.
- The first delivery is a coherent System/Agents experience, not every future projection or domain screen. Catalog may appear only as contextual relationships within those projections; a separate Catalog projection and a Commerce Customer projection are deferred.
- The World is a read projection. Owning domains remain authoritative and focused screens remain the mutation surfaces unless an explicitly approved part of this phase changes one.
- Contextual capability presentation is driven by the server rules in this packet, not a client capability registry or permanent workspace type. Empty-but-authorized Commerce setup remains reachable through one secondary setup action rather than permanent primary navigation.
- Knowledge-only and Commerce-enabled workspaces are equal permanent regression scenarios.
- Current Agent configuration, Playground, publishing, Channels, Conversations, handover and Knowledge behavior are integrated rather than rebuilt as parallel subsystems.
- Render the first World with accessible React DOM and SVG using a deterministic layout. Do not add PixiJS, D3, ELK, Motion or another visualization dependency. Test fixtures may exercise layout and state coverage but may never appear as production fallback data.
- Readiness is channel-specific and reuses current owning-domain rules. Website publication remains blocked unless its existing contract reports an allowed origin and at least one assigned Knowledge base or valid Catalog scope; Knowledge-only publication therefore remains valid. Facebook and Zalo connection/health are reported separately from Website publication. Missing future Actions is never a blocker.
- Conventional accessible navigation and structured information remain available alongside the spatial projection.
- User-visible wording changes are limited to the AppShell brand subtitle and navigation, workspace switcher labels, workspace overview, Agent list/workbench headings and actions, and create-workspace onboarding. Existing routes, request paths, source identifiers and untouched historical copy remain compatible.

## Schema Impact

No schema change is expected for the first slice. Existing Agents, revisions, Knowledge assignments, Channel bindings, Conversations, Contacts, analytics facts and Catalog scope remain authoritative.

If implementation discovery proves that a readiness fact cannot be derived safely from current state, the plan must identify the exact missing authoritative fact and obtain approval before adding persistence. The World itself never receives layout-authored business-state tables. User-specific ephemeral view preferences may remain client-side unless a separately approved cross-device requirement justifies storage.

## API Impact

Add `GET /api/v1/workspaces/{workspace_id}/overview?days=7|30` as the single initial read contract for the World; `days` defaults to `7` and rejects other values. It returns a domain-shaped response rather than renderer nodes, edges or coordinates. At minimum it contains:

- workspace identity and the actor's existing workspace role;
- `capabilities.catalog.available` and `capabilities.catalog.can_setup`, both computed server-side using the rules in this packet;
- an Agent collection ordered by stable public ID and capped at 50, with `agent_total` and `agents_truncated`; each item includes stable public ID, name, lifecycle state, update time and active published-revision summary when present;
- for each Agent, assigned-Knowledge summaries capped at 20, Channel bindings capped at 20 per provider and resolved Catalog references capped at 20 per relationship kind; every capped relationship includes its total and truncated state;
- for each Agent, Website/Facebook/Zalo binding and health summaries, Conversation/handover counts for the selected overview window, and safe machine-readable attention reasons from the bounded set `knowledge_stale`, `knowledge_failed`, `website_not_ready`, `channel_disconnected`, `channel_degraded` and `handover_pending`;
- a generated-at timestamp, the activity window and explicit dependency state so partial, stale or unavailable data is distinguishable from an empty collection; and
- stable owning-resource identifiers and route inputs, while presentation labels, layout coordinates and client selection state remain frontend concerns.

The endpoint must:

- derive workspace and role from authenticated membership;
- expose only server-authorized Agents and relationships;
- distinguish unavailable, partial and stale dependencies from empty state;
- use bounded counts/collections and stable identifiers;
- exclude document bodies, raw Conversation content, credentials and private provider payloads; and
- remain a read projection with no independent mutation contract.

Existing public/widget, Agent, Knowledge, Channel, Conversation, Contact, Analytics and Catalog contracts remain compatible.

## Frontend Impact

- Introduce the World at the workspace entry and integrate it with a contextual AppShell/navigation model.
- Implement the World as deterministic React DOM/SVG. DOM owns headings, controls, the inspector and structured/list fallback; SVG owns only the spatial relationships and non-interactive visual connectors that benefit from it.
- Reuse current design tokens, feedback/error handling, workspace switching, Agent workbench, Playground and channel panels.
- Replace misleading user-visible “shop/chatbot” wording in the AppShell brand subtitle/navigation, workspace switcher, workspace overview, Agent list/workbench and create-workspace onboarding. Do not mechanically rename code, routes or unrelated copy.
- Establish clear ownership among DOM/SVG rendering, the inspector, navigation and focused screens according to the World technical specification.
- Keep selection/focus/navigation state separate from authoritative domain data.
- Render all user/provider/model-derived text as untrusted content and maintain current evidence-rendering rules.

## Security Impact

- Every projection request authenticates the dashboard actor and scopes all relationships server-side to current workspace membership.
- Agent, Knowledge, Channel, Conversation, Contact, Catalog and public IDs identify candidates but never grant access.
- Client navigation state cannot enable a capability, widen Agent scope or reveal hidden resources.
- Counts, attention reasons and readiness state must not leak another tenant's records, private content, provider secrets or inaccessible member activity.
- Role-denied actions remain absent or clearly read-only without making authorization decisions solely in the client.
- No private source snippets, Conversation transcripts or provider payloads are required in the overview.

## Test Plan

- Permanent scenario tests cover a Knowledge-only workspace with no Catalog records and a Commerce-enabled workspace with validated Catalog scope.
- Multi-Agent fixtures verify Agent/Knowledge/Channel/Conversation relationships, stable selection and no cross-Agent or cross-workspace mix-up.
- Tenant tests use two workspaces with similar identifiers and deny every cross-workspace projection and deep-link path.
- Navigation tests prove absent capabilities leave no broken route, empty placeholder or required Commerce setup while current deep links remain reachable.
- Lifecycle tests cover create/configure/test/publish/observe paths, real draft/published/paused state and honest readiness blockers.
- State tests cover loading, empty, partial, stale, disconnected, degraded, failed, forbidden and needs-attention rendering without fake fallback data.
- Information-ownership tests prove important facts are not needlessly duplicated between World, inspector and same-screen cards.
- Interaction tests cover pan/zoom where used, semantic zoom, selection, focus, inspector handoff, history/deep-link behavior and stable layout.
- Accessibility tests cover keyboard operation, focus restoration, semantic alternatives, screen-reader labels, non-color state, reduced motion and conventional-navigation parity.
- Responsive tests cover 1440, 1024, 768, 390 and 320 widths with usable list/detail or tab fallbacks.
- Performance tests follow the World specification budgets and verify bounded requests/no per-Agent N+1 loading.
- Projection contract tests verify Catalog `available`/`can_setup`, channel-specific readiness, bounded collections, partial dependency state and the absence of renderer/layout fields.
- Existing Agent, Knowledge, Channel, Conversation, Contact, Analytics, Catalog and widget regressions remain green with fake providers only.
- Documentation verification includes phase/link/status consistency, stale legacy phase references and `git diff --check`.

## Acceptance Criteria

- A Knowledge-only workspace renders a coherent Agent/Knowledge/Channel/Conversation experience with no Catalog, Inventory, Order, POS or Commerce Customer requirement or empty Commerce placeholder.
- A Commerce-enabled workspace retains current Catalog assignment, focused management and validated product-evidence paths without making Commerce universal.
- The workspace can show multiple Agents and their real assigned Knowledge, bound Channels, bounded Conversation/handover activity and contextual domain access from authoritative data.
- An operator can select an Agent and reach identity/instructions, Knowledge, current domain access, Test, publish/deploy, Conversations and human-intervention paths without understanding tool schemas or a capability registry.
- Draft, published, paused, disconnected, degraded, forbidden and needs-attention states are distinguishable in text and never fabricated.
- Each important fact has one clear visual owner on the overview; the inspector adds contextual detail rather than repeating filler cards.
- Capability-aware navigation hides absent domain areas while preserving direct, accessible access to every currently implemented function the actor may use.
- World selection/focus, focused-screen handoff and browser navigation are deterministic and do not mutate domain state.
- Keyboard, screen-reader, visible-focus, reduced-motion and structured/list alternatives meet the World acceptance criteria; the spatial view is never the only usable path.
- The experience remains usable at 1440, 1024, 768, 390 and 320 pixels and does not depend on hover alone.
- Projection loading is bounded and avoids per-Agent N+1 requests; partial dependency failure remains visible rather than displayed as empty success.
- A workspace with no Catalog data hides Catalog, Locations and Collections from primary navigation; an authorized manager can still reach one Commerce setup action, while an unauthorized actor cannot see it.
- Website readiness exactly preserves the current allowed-origin plus Knowledge-or-Catalog rule; Facebook/Zalo health does not masquerade as Website publish readiness, and missing future Actions never blocks publication.
- The production World uses deterministic DOM/SVG and authoritative API data, with no runtime fixture fallback or new visualization dependency.
- Existing APIs, identifiers, publication/channel behavior, tenant isolation, Knowledge-only runtime and Commerce evidence remain compatible.
- No effectful Action, speculative framework, fake product state, 3D game treatment or unapproved dependency is introduced.

## Approved Implementation Boundary

- The owner approved this packet's first-slice direction, information hierarchy, deterministic DOM/SVG renderer, projection contract boundary, capability/navigation behavior, readiness semantics and bounded copy changes.
- Implementation may refine field names to match established Python/TypeScript conventions, but it may not change the declared ownership, security, capability, readiness or scope semantics without returning the packet to owner review.
- Any Canvas/WebGL renderer, visualization dependency, schema migration, separate Catalog/Customer projection, generic capability registry or broader route rename requires a new plan and explicit owner approval.
