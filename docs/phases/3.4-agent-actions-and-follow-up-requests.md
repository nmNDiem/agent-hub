# 3.4 — Agent actions and natural follow-up requests

Status: **Complete — 2026-10-20**

## Implemented Contract

The shipped slice adds the single typed `contacts.follow_up.request` action. Its execution context is bound by the server to the current workspace, Agent, immutable revision, Conversation, inbound message and Channel connection. The Contacts-owned service revalidates those references and the live permission in a separate transaction, then atomically records redacted execution evidence and creates or reuses one Lead per Conversation.

Website requests require a validated email or phone. Facebook and Zalo requests use only the existing server-resolved provider Contact identity. Compatible replays return the existing result; conflicting normalized input fails closed. Playground never receives the effectful tool, and disabling the live Agent permission blocks execution immediately even when an older published revision enabled it.

The existing Agent screen owns the opt-in toggle. Existing Lead, Contact timeline and Conversation detail surfaces show safe channel, capture-source, revision and outcome provenance. Action evidence contains identifiers, hashes, status/codes and timing only and expires with the shorter applicable Lead/Conversation retention boundary; it does not copy message text, contact data, provider identities, prompts or raw tool arguments.

The implementation preserves the existing Website consent form as a distinct flow and does not add a generic action API, registry, workflow engine, proactive delivery or SLA promise. Privacy/compliance review of the conversational disclosure and evidence remains a production release gate.

## Goal

Prove the minimum safe effectful Agent-action boundary through one concrete, low-risk workflow: during a real Website, Facebook Messenger or Zalo conversation, an authorized published Agent can record a customer's explicit request for human follow-up in the existing Contacts/Leads domain without a mechanical confirmation step, inventing consent, or building a general action platform.

## User-visible outcome

A customer can ask naturally for a person or business to contact them. The Agent asks only for information that is actually missing, records the request once, and responds conversationally that it has been passed to the business without claiming a response time or staffed availability. Workspace operators see the request in the existing Leads, Contact and Conversation workflows with its Agent, revision, channel, conversation, status and safe execution provenance.

## Existing Behavior to Preserve

- Website callback capture continues to require its current explicit form consent, scoped visitor token, matching active conversation, contact method, consent-text version, request hash, idempotency key and retention boundary.
- Existing Website callback UI remains an optional customer-initiated fallback; this phase does not remove it or force the Agent-action path through it.
- Contacts remain workspace-level communication identities. Leads remain follow-up state and never become Commerce Customers automatically.
- Verified Facebook/Zalo inbound already creates or links a connection-scoped provider identity. The model cannot choose, forge, merge or reassign that identity.
- Contact merging remains exact-evidence, owner/admin, reasoned, version-checked, auditable and reversible. Agent output never performs identity resolution or merge.
- Conversations continue to own channel provenance, participant messages, AI/human mode, assignment, unread state, lifecycle and delivery truth.
- Channel adapters verify and normalize provider events before runtime work. Duplicate events cannot create duplicate messages, model turns, action executions or Leads.
- Facebook's 24-hour and Zalo's 48-hour response windows, opt-outs, provider permissions, delivery certainty and human takeover fencing remain independently enforced.
- Published channel execution remains associated with one immutable Agent revision. Existing Knowledge-only and Commerce-enabled read behavior remains compatible.
- Current Lead list, status updates, CSV safety, retention cleanup, role restrictions and tenant hiding remain compatible.
- Routine logs and public mutation responses do not contain email, phone, raw conversation text, provider identity values, prompts or secrets.

## Scope

- Introduce one stable typed action identifier, `contacts.follow_up.request`. It records an internal request for a human to follow up; it does not itself send a proactive message, assign a staff SLA, place an order, book an appointment or call an external provider.
- Make this action explicitly configurable for each Agent. Enabling it is an owner/admin operation and becomes executable only through a published revision that snapshots the enabled state. Disabling the live capability is fail-closed and takes effect for current channel execution without waiting for another model turn.
- Expose the action to the runtime only when all server-derived prerequisites hold: the Agent/revision permits it, the conversation is active and in AI mode, the inbound turn belongs to that conversation and authorized channel/session, the Contact or Website reachability rules can be satisfied, retention permits the write, and no human takeover or provider revocation has invalidated execution.
- Treat model tool arguments as untrusted. The tool may propose a bounded name, email or phone and a source inbound message reference, but it cannot provide workspace, Agent, revision, Conversation, Contact, channel/provider identity, permission, consent state, retention, status or audit attribution.
- Require the action to be grounded in the current customer turn or an immediately preceding unambiguous affirmative reply to the Agent's follow-up offer. The server validates message identity, direction, conversation ownership, channel provenance, ordering and bounded age. The runtime policy must ask a natural clarifying question rather than execute when the request or required reachability is ambiguous.
- Do not require a second confirmation prompt, modal, form or checkbox after the customer has already explicitly asked for follow-up or clearly accepted the Agent's offer. Interest, sentiment, product questions, browsing behavior and model-estimated lead quality are not sufficient evidence.
- For Website conversations, require a valid email or phone supplied by the customer in the conversation or through the existing callback form. The Agent asks naturally for one missing contact method and never claims it already knows an anonymous visitor's identity.
- For Facebook/Zalo conversations, use only the server-resolved verified provider Contact identity and current Conversation as the follow-up route. Email or phone is optional unless the customer voluntarily supplies it. Provider IDs never appear in model arguments, public DTOs or normal logs.
- Reuse the existing Contact and Lead domain service rules. Extend them narrowly so a social Lead can be reachable through its verified provider identity without fabricating a `widget_session`, email or phone. Preserve one Lead/follow-up record per Conversation unless the existing domain lifecycle proves a concrete need for a later request.
- Persist a narrow Contacts-owned execution record before the Lead mutation is applied in the same transactional boundary. It records the fixed action identifier, workspace, Agent, immutable revision, Conversation, source message, Contact where resolved, idempotency key, request hash, state, safe outcome reference, safe error code and timestamps. It does not copy message text, email, phone, provider IDs, prompts or raw tool arguments.
- Use a server-generated execution/idempotency identity derived from persisted turn/conversation context rather than accepting a model-generated key. Replays return the prior compatible result; a reused key or source turn with conflicting normalized contact data fails explicitly.
- Keep the effect atomic because this first action changes PostgreSQL state only. Claim execution, create or reuse the authorized Contact/Lead, attach safe provenance and mark success in one transaction. A rollback leaves no partial Lead; a committed success is discoverable even if the subsequent Agent response or channel delivery fails.
- Represent execution states narrowly as needed for this workflow, including at least executing/claimed, succeeded and failed-terminal or retryable-failure semantics. Do not introduce provider reconciliation or an `outcome_unknown` state when no external side effect exists.
- Return a bounded typed tool result that tells the runtime whether the request was recorded, already existed, needs missing information, was denied or failed safely. The model may render a natural response but cannot rewrite the authoritative result or promise timing, assignment or availability.
- Show safe action provenance in the existing Leads, Contact timeline and Conversation/Inbox context: originating channel, Agent/revision, request time, current Lead status and whether execution succeeded or was a replay. PII visibility continues to follow current Contact/Lead role rules.
- Add clear operator configuration and readiness copy explaining what the action does, which published channels can execute it and that it creates a follow-up request only after a customer's explicit conversational request or acceptance.
- Add bounded operational metrics for attempted, succeeded, replayed, denied and failed executions using safe IDs/codes/counts only.
- Update only authoritative Agent, Contact/Lead, Conversation, Channel, API, data-model, security, testing, operations and UI documentation whose implemented contracts change.

## Non-goals

- A universal action/tool registry, capability marketplace, plugin system, arbitrary webhook caller, workflow engine, rules engine or general approval service.
- A general `agent_tool_calls` ledger, global audit-log platform or reusable execution API for actions that do not yet exist.
- Native Facebook quick replies, Messenger templates, Zalo templates, Zalo Mini Apps or provider-specific forms. The first slice must work through normalized text conversations and existing verified identities.
- Automatic lead scoring, sentiment-based capture, behavioral profiling, marketing audience creation, campaign enrollment or inferred consent.
- Proactive marketing, broadcast, cold outreach, automated follow-up delivery or bypass of provider response windows and opt-outs.
- A guarantee that a human is online, will reply within an SLA or will use a particular contact method.
- Contact merge, Customer promotion, appointment booking, email/document sending, order/payment/inventory mutations or any Commerce action.
- Letting an Agent edit Lead status, Contact notes, tags, assignment or conversation handling mode.
- Effectful Playground execution, fake Leads created by operator tests, or a dry-run framework. Playground may explain that the action requires a real published conversation.
- Removing the existing Website callback form or changing its consent contract as part of the action slice.
- Retaining duplicate conversation text or PII in action evidence, analytics, logs or model-visible action results.

## Confirmed Decisions

- The first effectful action is a natural omnichannel human-follow-up request, not a Website-only lead form and not a generic action foundation detached from a workflow.
- Website, Facebook Messenger and Zalo are supported through one normalized business outcome. Provider-specific identity and response-window semantics remain adapter/domain concerns; identical UI affordances are not required.
- This low-impact internal record does not require a second mechanical confirmation after an explicit customer request or clear conversational acceptance. The originating customer message is the evidence; ambiguous interest requires clarification and cannot trigger the action.
- A model cannot declare that consent exists. It can request the typed action against a bounded source message; server policy establishes provenance and eligibility, while the Contacts domain owns the resulting Lead and retention rules.
- Social reachability is the verified provider identity plus Conversation. The database and API must not fabricate email, phone or Website session ownership to reuse the existing Lead path.
- The action has no external side effect. Any later outbound human reply remains a Conversation/Channel operation subject to assignment, handling mode, provider window, opt-out and delivery policy.
- Authorization is both per-Agent and per-published-revision, with a fail-closed live revocation check. Instructions or model output cannot enable the action.
- Execution evidence is narrow and action-specific. It may establish the minimum pattern needed by this action but does not register or authorize future actions.
- One transactional PostgreSQL boundary is sufficient for this workflow; external reconciliation and ambiguous-provider-effect machinery would be speculative.
- Existing Website callback capture remains supported and distinct. It may converge on shared domain internals only if behavior, consent versioning, idempotency and API compatibility are preserved.
- Target release assumptions are Vietnam-first and reuse the current 30-day consented Lead retention default. Release review must confirm that the conversational disclosure, purpose and evidence meet the applicable personal-data policy; this packet is not legal advice.

## Schema Impact

Additive Alembic migrations are expected.

The Agent draft requires one concrete follow-up-action enablement flag, and immutable Agent revisions require the snapshotted value. A generic capability registry or polymorphic action configuration table is not justified by one action. Existing revisions backfill to disabled so publication behavior does not silently gain mutation authority.

The current Lead schema assumes a Website session and at least one email/phone value. Evolve it without replacing the aggregate so a Lead may instead be reachable through a verified social Contact identity and Conversation. Website-created Leads retain their current session/contact-method constraints; social creation requires a supported provider Conversation and a server-resolved Contact identity. Cross-field/database constraints should enforce the valid Website-versus-social shapes rather than making every relationship weakly nullable.

Add a narrow Contacts-owned follow-up execution table or equivalently scoped record. It must support:

- workspace-consistent foreign keys to Agent, Agent revision, Conversation, source message, Contact and Lead outcome;
- a fixed/checked action identifier for this workflow;
- server-generated idempotency identity and request hash uniqueness;
- bounded checked state and safe error code;
- created/started/completed timestamps; and
- indexes for replay lookup, operator provenance and retention cleanup without querying across tenants.

The execution record stores references and hashes, not duplicate message content, contact details or provider identity values. Its sensitive references follow the owning Conversation/Contact retention boundary; any content-free retained fact after expiry must not restore access to deleted PII.

No schema may make Qdrant, a model response or a provider payload authoritative. Generated migration artifacts are created through Alembic and are not manually edited after generation except according to existing migration conventions.

## API Impact

Extend the authenticated Agent configuration DTOs with one explicit `follow_up_action_enabled` field and preserve strict extra-field rejection. Publishing snapshots the field into the immutable revision. Current Agents and revisions default to false.

Extend Lead/Contact timeline/Conversation responses only with the minimum safe provenance needed by operators, such as source channel, Agent revision reference, request time and action outcome. Do not expose raw provider identity, source-message text through a new field, internal request hashes or execution internals.

No public generic action endpoint is added. Published runtime execution invokes the typed action internally after server-side context resolution. The existing Website callback route and response shape remain compatible.

If a focused authenticated execution-detail endpoint is necessary for operator error visibility, it is nested under the owning Contact/Lead or Conversation resource, uses existing role and assignment visibility, returns safe status/error fields only and cannot retry or mutate the action. A workspace-wide `/actions`, arbitrary tool invocation route or public action-history API is prohibited.

Stable errors distinguish disabled/unauthorized action, stale or mismatched evidence, missing Website contact method, already-recorded compatible request, idempotency conflict, invalid contact data, human-takeover fence, expired/revoked context and retryable internal failure. Cross-workspace and cross-conversation references follow existing non-disclosure conventions.

## Frontend Impact

Add a focused toggle and concise explanation to the existing Agent configuration flow; do not create a new action-builder screen. Enabling is visibly part of the draft and requires publish to grant the immutable revision. Disabling uses the approved immediate fail-closed behavior and the UI must explain any draft/published distinction.

The existing Website callback form remains available. The Agent-driven flow stays inside normal chat: the Agent asks naturally for missing Website contact information and acknowledges a recorded request without opening a forced confirmation dialog or claiming staff availability.

Facebook and Zalo need no new AgentHub-rendered customer form in this phase. Text responses remain usable when native interactive features are unavailable. Provider identity is never displayed as a substitute phone/email value.

Leads, Contact timeline and Inbox/Conversation context show compact provenance and state through existing components. Operators can distinguish a manual Website form submission from an Agent-recorded conversational request and can navigate to the originating conversation subject to current access rules.

UI states cover disabled, unpublished change, unavailable in Playground, missing reachability, recorded, replayed/already recorded, forbidden, expired context and safe failure. Status and errors are accessible, do not rely on color alone and never reveal PII to roles that cannot already view it.

## Security Impact

- Every execution derives workspace, Agent, immutable revision, Conversation, source message, Contact/provider identity, channel, actor and retention context on the server. Tool arguments cannot widen or replace them.
- The action is absent from model tools unless current Agent permission and published-revision permission both allow it. Live disable, pause, archive, human takeover, revoked channel binding and expired Website session fail closed.
- The source message must be an authenticated/scoped Website inbound message or a verified/deduplicated Facebook/Zalo inbound event in the same Conversation. A guessed UUID, replay from another conversation or outbound/assistant message never supplies evidence.
- Model output is not trusted to establish identity, permission or consent. The low-impact policy accepts only an explicit request or clear acceptance in bounded current conversational context; ambiguous cases produce a question and no mutation.
- Name, email and phone inputs use current validation and normalization. Contact resolution never merges by name, model inference or unverified contact data.
- Public/social provider identity stays in existing private mappings. It is not copied to tool payloads, public DTOs, prompts, metrics or logs.
- Execution evidence records IDs, hashes, status, timestamps and safe codes only. Conversation text, email, phone, provider payloads, prompts, raw arguments and credentials are excluded.
- Replays are idempotent, payload conflicts fail explicitly, concurrent requests cannot create two Leads, and a rolled-back database transaction cannot leave a successful execution pointing at absent domain state.
- The action creates an internal follow-up record only. It cannot send proactive messages, override opt-out/window rules, promise availability, change handling mode or invoke another domain mutation.
- PII access, retention and deletion remain controlled by Contacts/Conversations. Expiry must remove or sever sensitive references so action history cannot reconstruct deleted content.
- Rate limits, runtime tool budgets and workspace quotas bound repeated attempts. Denial and failure metrics use codes/counts rather than customer content.

## Test Plan

- Migration rehearsal covers upgrade, constraints, indexes, current Website Leads, current Agent revisions defaulting disabled, representative Facebook/Zalo Contacts, retention cleanup and practical downgrade/rollback.
- Agent authorization tests cover owner/admin enablement, member denial, publish snapshot, old-revision disabled behavior, current live disable, paused/archived Agent, forged configuration and unpublished changes.
- Runtime tests prove the action definition is absent when unauthorized and available only in eligible published conversations. Knowledge-only and Commerce-enabled Agents retain their current read behavior.
- Website tests cover an explicit callback request with valid phone/email in conversation, natural missing-information follow-up, existing form compatibility, stale/foreign session denial and no second confirmation after an explicit request.
- Facebook and Zalo tests cover verified provider Contact identity, no required email/phone, response-window/opt-out preservation, duplicate/reordered webhook events, revoked connection, human takeover and safe text acknowledgment.
- Intent-boundary regression cases cover direct requests, clear affirmative replies, refusals, corrections, ambiguous interest, product questions, prompt injection, quoted instructions, an Agent suggestion with no customer reply and attempts to create a Lead from assistant-authored text.
- Tenant-isolation tests use two workspaces with similar Agent, revision, Conversation, message, Contact and Lead identifiers and deny every cross-workspace or cross-conversation evidence/action lookup.
- Validation tests cover invalid/oversized name, email and phone; model-supplied workspace/Contact/provider/consent/status fields; mismatched source-message direction; stale evidence; deleted Contact; expired retention and unsupported channel state.
- Idempotency/concurrency tests cover repeated tool calls, response-job retries, duplicate provider events, concurrent execution, compatible replay, conflicting normalized data and rollback before commit. Exactly one Lead and one successful execution result are observable.
- Execution-state tests prove the record is claimed before mutation in the transaction, success references the correct Lead, safe failures expose stable codes, committed success survives later model-response/delivery failure and no partial authoritative state remains after rollback.
- Contact/Lead tests preserve existing Website session/contact requirements, social provider reachability constraints, one-Lead-per-Conversation behavior, status workflow, CSV injection protection, role visibility and 30-day cleanup.
- Redaction tests inspect API responses, structured logs, metrics and execution rows for absence of raw messages, PII, provider identities, prompts, tool arguments and credentials.
- Frontend tests cover toggle/publish state, immediate-disable explanation, Lead/Inbox provenance, role-restricted PII, accessible states and the lack of a forced customer confirmation UI.
- Automated tests use fake model, channel and delivery providers and make no paid provider calls. Documentation verification includes packet/link/status consistency and `git diff --check`.

## Acceptance Criteria

- An owner/admin can enable the concrete follow-up action for an Agent, publish it into an immutable revision and disable execution fail-closed; unauthorized roles and old disabled revisions cannot execute it.
- A published Agent can record one human-follow-up request from an explicit customer request or clear acceptance in a real Website, Facebook or Zalo conversation without a second mechanical confirmation step.
- Ambiguous interest, browsing, product questions, refusal, silence and model inference do not create a Lead; the Agent asks a natural clarifying question when necessary.
- Website execution requires a validated customer-supplied email or phone, while Facebook/Zalo execution uses only the verified server-resolved provider Contact identity and never fabricates Website session or contact data.
- The action invokes the Contacts/Leads domain service under server-derived workspace and Conversation scope. Model output cannot select identity, permission, consent, retention, status or attribution.
- A narrow durable execution record exists before the Lead mutation in the same atomic transaction and identifies the action, Agent revision, Conversation, source message, idempotency state, outcome and safe timing without copying customer content or PII.
- Duplicate tool calls, webhook replay, response-job retry and concurrency produce one compatible Lead/action result; conflicting replays fail explicitly and rollback leaves no partial state.
- Operators can see safe request provenance and current Lead state in existing Leads, Contact and Conversation workflows without a generic action console or expanded PII access.
- A committed Lead remains visible if the Agent's later response or channel delivery fails; the action never claims that a human is available or that follow-up was delivered.
- Existing Website callback capture, Contacts/Lead workflows, Inbox/handover, provider windows/opt-outs, Agent publication, Knowledge-only behavior, Commerce read tools, retention and CSV safety remain compatible.
- Tenant denial, role enforcement, identity validation, human-takeover fencing, redaction, retention cleanup, channel replay and fake-provider coverage pass for all new surfaces.
- No action registry, plugin framework, workflow engine, generic audit system, native provider-template dependency, proactive messaging or unrelated domain mutation is introduced.

## Blocking Owner Decisions

Approval of this packet confirms all of the following release decisions:

- The customer experience is conversational. An explicit request such as asking the business to call/message them, or a clear affirmative response to the Agent's offer, authorizes this low-impact internal follow-up record without an additional checkbox or “Are you sure?” step.
- The existing Website callback form and its explicit consent checkbox remain available as a separate fallback; this phase does not remove or weaken it.
- Website needs a customer-supplied email or phone. Facebook/Zalo may create the Lead from the verified provider identity and originating Conversation with no email/phone.
- The action is opt-in per Agent, snapshotted at publish, and can be revoked immediately from live execution by an owner/admin.
- One Lead per Conversation remains the first-slice rule; repeated compatible requests replay the existing result rather than create a new Lead.
- The action records a request only. It does not promise an SLA, automatically assign staff or send proactive follow-up.
- Vietnam is the first release jurisdiction, current 30-day Lead retention remains the default, and a privacy/compliance review of conversational disclosure/evidence is required before production release.
- Native Facebook/Zalo buttons or templates are deferred; normalized text must remain the complete functional fallback.
