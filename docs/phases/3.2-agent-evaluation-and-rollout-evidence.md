# 3.2 — Agent evaluation and rollout evidence

Status: **Next candidate — not approved for implementation**

## Goal

Give workspace operators repeatable evidence about Agent quality before rollout and a focused way to review real unresolved interactions after rollout, without making model output, opaque scores or traffic automation authoritative.

## User-visible outcome

An authorized operator can maintain representative evaluation cases, run the same versioned case set against a baseline and a candidate Agent target, review deterministic and human-assessed results, compare regressions, and record a rollout decision. Operators can also triage explicitly signaled unresolved production responses and convert suitable examples into sanitized evaluation cases.

## Existing Behavior to Preserve

- Published revisions remain immutable and existing Website, Facebook and Zalo bindings continue to use their selected revision.
- Evaluation never publishes, promotes, pauses or rebinds an Agent as a side effect of running or approving a comparison.
- Knowledge-only Agents expose no Catalog tools or product rendering; Commerce-enabled Agents retain validated Catalog scope and product evidence.
- Conversation content remains owned by Conversations and subject to its authorization and retention lifecycle.
- Operational analytics definitions, usage accounting, tenant isolation, quotas and provider-call boundaries remain intact.
- Existing public/widget sessions gain no dashboard access and cannot use public identifiers as authorization.

## Scope

- Add workspace-owned evaluation suites and versioned case sets with bounded prompts, expected behaviors and explicit check definitions.
- Support deterministic checks for required or forbidden response properties, valid source/product evidence, safe fallback behavior and capability boundaries; support an attributable human verdict where correctness cannot be reduced to an exact string.
- Execute a frozen case-set version against explicit immutable baseline and candidate targets through the existing bounded Agent runtime and fake provider in automated tests.
- Persist run provenance sufficient to reproduce and interpret a comparison: Agent target, case-set version, runtime/model configuration identifiers, timestamps, outcome, usage facts and per-case results.
- Compare baseline and candidate by added passes, fixed failures, new regressions, unchanged failures and unevaluated cases. Missing or failed runs remain visible and are never counted as passes.
- Capture narrowly defined feedback on a specific completed assistant response and retain attribution, category, optional bounded comment and timestamps according to the approved actor and retention policy.
- Provide an unresolved-review queue built from explicit persisted signals such as negative feedback, an operator mark or a recorded response failure. Do not infer resolution from sentiment or an unversioned model classifier.
- Allow an authorized reviewer to classify a review item, resolve it, and create a new sanitized evaluation case through an explicit copy/review step rather than silently copying production content.
- Produce durable rollout evidence that records the compared targets, thresholds, result summary, reviewer and decision. Approval records evidence only; rollout remains a separate existing publish/binding action.
- Add focused dashboard states for suite/case management, run status, comparison, feedback triage and recorded rollout decisions.
- Update only the authoritative domain and cross-cutting documents whose implemented behavior changes.

## Non-goals

- Automatic publication, revision promotion, rollback, traffic splitting, canary routing or provider experimentation.
- An LLM-as-judge requirement, opaque universal quality score or claim that offline evaluation proves production success.
- Automatic harvesting of conversation text, documents, contact data or visitor identity into evaluation datasets.
- Knowledge freshness, ingestion recovery or retrieval diagnostics owned by phase 3.3.
- Prompt optimization, self-editing Agents, autonomous remediation or automatic case generation.
- A generic event warehouse, experiment platform, plugin registry, workflow engine or general model-observability product.
- Effectful tools, orders, payments, refunds, stock mutations or new channel providers.

## Confirmed Decisions

- Evaluation cases and case-set versions are workspace-owned, explicitly curated records rather than source files hidden only in application tests.
- A comparison is meaningful only when the case-set version and both runtime targets are immutable and recorded.
- Deterministic policy/evidence checks and attributable human review are the default evaluation mechanisms; model grading is optional only after explicit approval of its rubric, provider, cost and limitations.
- Aggregate scores never hide per-case regressions, execution errors, skipped cases or missing evidence.
- Production feedback references the owning message/conversation and does not duplicate full conversation transcripts.
- Creating a case from production content requires explicit review and sanitization before the case becomes reusable.
- Rollout evidence is advisory and auditable. It cannot mutate publication or channel bindings.
- Analytics may summarize persisted evaluation facts but does not own evaluation cases, verdicts or production message content.

## Schema Impact

An additive migration is expected for evaluation suites, immutable case-set versions/cases, runs/results, response feedback or review state, and rollout-decision evidence. Final table boundaries depend on the blocking decisions below.

Every tenant-owned relationship must enforce workspace consistency. Run and decision records must retain the immutable identifiers needed for interpretation without duplicating Agent, Conversation or message content. Deletion and retention behavior must preserve factual decision history while removing expired sensitive text.

No existing Agent revision, Conversation, message, analytics-event or usage table is renamed or repurposed.

## API Impact

Additive authenticated dashboard endpoints are expected for evaluation suite/case management, run initiation/status, baseline comparison, feedback/review triage and rollout decisions. Lists must use bounded pagination/filtering; mutations require CSRF, role checks, validation and idempotency where retries can duplicate work.

Run responses must distinguish queued, running, completed, partially failed, failed and canceled outcomes where supported. Comparison payloads must expose denominators and per-case state rather than only an aggregate percentage.

No public feedback endpoint is authorized until its actor, abuse controls, session/message proof, idempotency and retention policy are approved.

## Frontend Impact

Add a focused evaluation workflow reachable from the Agent workbench or Analytics without replacing existing navigation. It must show target identity, case-set version, execution status, usage/cost availability, per-case evidence, regressions and reviewer decisions.

The unresolved-review surface must distinguish negative feedback, operator marks and runtime failures; preserve filters across refresh where consistent with current UI conventions; and provide loading, empty, partial, error and forbidden states. Charts or scores require an accessible tabular alternative and must never use color alone to indicate regression.

## Security Impact

- Evaluation execution derives workspace, Agent, revision and Knowledge/Catalog scope on the server; request IDs and case IDs never grant access.
- Evaluation prompts, expected answers, retrieved text, model output, feedback comments and copied production examples are untrusted and may contain sensitive data or prompt injection.
- Role checks must separate read, edit, execute, review and rollout-decision authority according to the approved permission model.
- Provider calls obey existing quotas, concurrency limits, redacted logging and usage accounting. Automated tests use fake providers and never incur paid calls.
- Public feedback, if approved, must bind to the exact origin/session/conversation/message, reject expired or cross-session access, rate-limit abuse and avoid exposing whether unrelated messages exist.
- Retention cleanup must revoke authoritative access before best-effort external cleanup and must not leave copied production content outside its approved lifecycle.

## Test Plan

- Migration rehearsal covers upgrade, constraints, indexes, representative backfill if any, and practical downgrade/rollback.
- Tenant tests use two workspaces with similar Agent, revision, case and message identifiers and deny every cross-workspace read/write/run/review path.
- Evaluation tests cover immutable case-set versions, bounded inputs, duplicate/idempotent run requests, partial provider failure, cancellation/fencing where applicable, and preservation of per-case error states.
- Comparison tests cover fixed failures, new regressions, unchanged results, skipped/unevaluated cases, changed denominators and deterministic ordering.
- Runtime tests prove the same server-authorized capability and evidence validation rules apply during evaluation as in Playground/channel execution.
- Permanent suites include both a Knowledge-only Agent with no Commerce records and a Commerce-enabled Agent with Catalog scope and validated product evidence.
- Feedback/review tests cover allowed actors, exact message binding, duplicate submissions, expired content, retention cleanup, sanitization before case creation and forbidden/cross-session cases if public feedback is approved.
- Rollout-decision tests prove a recorded approval or rejection cannot publish, pause, promote or rebind an Agent.
- Frontend tests cover accessible case editing, run progress, per-case comparison, regression emphasis, review actions and loading/empty/partial/error/forbidden states.
- Documentation verification runs link/status consistency checks and `git diff --check`; no live provider evaluation is run without separate owner approval and a declared budget.

## Acceptance Criteria

- An authorized workspace operator can create and version an evaluation suite containing representative Knowledge-only and Commerce cases.
- The same frozen case-set version can run against immutable baseline and candidate targets without changing live publication or channel bindings.
- Results preserve target/config provenance, explicit per-case outcomes, usage facts and errors; missing results are never treated as passes.
- A comparison clearly identifies new regressions, fixed failures, unchanged failures and denominator changes and supports an attributable human review.
- Explicitly signaled unresolved responses can be reviewed without copying full conversation content, and any new reusable case requires deliberate sanitization.
- Rollout evidence records thresholds, compared targets, result summary, reviewer and decision while leaving rollout as a separate action.
- Tenant denial, role enforcement, CSRF, idempotency, retention and fake-provider coverage pass for every new surface.
- Existing Knowledge-only, Commerce, published-revision, channel, quota and retention behavior remains compatible.
- No automatic rollout, opaque quality claim, unapproved paid model judging or speculative evaluation framework is introduced.

## Blocking Owner Decisions

- Approve the permission model: whether suite editing, run execution, review and rollout decisions are owner/admin-only or whether selected member operations are allowed.
- Approve the immutable candidate mechanism: a non-live evaluation revision, a frozen draft snapshot, or another explicit target that does not replace the currently published revision.
- Approve feedback sources for this phase: dashboard operators only, Website visitors, or all supported channels; define whether a rating, categorized reason and optional comment are required.
- Approve retention periods for evaluation prompts/outputs, feedback comments, review links and rollout evidence, including what survives Conversation content expiry.
- Approve rollout thresholds and whether they are workspace-configurable or a documented fixed first-slice policy.
- Approve whether any real-provider evaluation or model grading is in scope, including provider/model allowlist, concurrency, quota treatment and budget. Until then, implementation and automated verification must use fake providers only.
- After these decisions are resolved, the owner must explicitly change this packet to **Approved for implementation** before coding begins.
