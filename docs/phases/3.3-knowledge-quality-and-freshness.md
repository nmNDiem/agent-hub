# 3.3 — Knowledge quality and freshness

Status: **Implemented — approved 2026-10-16**

## Goal

Give workspace operators trustworthy visibility and bounded controls for keeping Knowledge current, understanding which immutable source version is searchable, recovering failed ingestion, and diagnosing retrieval without treating Qdrant, model output or an opaque quality score as authoritative.

## User-visible outcome

An authorized operator can see when a source was last reviewed and when it needs attention, replace its content through an immutable version, follow that version through ingestion to active search, recover supported failures without losing the last good version, and run a scoped diagnostic query that explains which permitted sources were searched and which validated chunks were returned.

## Existing Behavior to Preserve

- PostgreSQL remains authoritative for sources, immutable versions, generations, chunks, activation and ingestion state; Qdrant remains a filtered, revalidated and rebuildable projection.
- Only a complete ready generation is searchable, and active-generation cutover is atomic.
- A failed replacement or rebuild cannot revoke the last good active generation merely because newer work exists.
- Manual text and private PDF/TXT sources retain current size, media validation, storage and retention boundaries.
- Durable ingestion keeps its leases, fencing, heartbeat, classified retry behavior, attempt evidence and single-active-job constraint.
- Retrieval injects workspace and allowed-source filters on the server and revalidates returned chunks against active PostgreSQL state.
- Knowledge-only Agents remain independent of Commerce; Catalog price, SKU, options and inventory never move into RAG.
- Existing published revisions, Website/Facebook/Zalo execution, source references, quotas and tenant denial remain compatible.

## Scope

- Define explicit source freshness metadata for current manual/file sources: last confirmed review, optional review cadence or next-review time, reviewer attribution and a server-derived state such as unknown, current, due soon or overdue.
- Present freshness as an operator-maintained review signal, not proof that content is correct and not an automatic reason to remove an otherwise valid active source from retrieval.
- Add a replacement flow that creates a new immutable version of an existing document rather than overwriting source text or media. Preserve content hash, source kind, creator and creation time as version provenance.
- Detect a byte-identical or normalized-identical replacement where practical and return an explicit no-change/conflict result instead of creating needless ingestion work.
- Expose bounded version history with version number, source metadata, ingestion/generation state, activation state, timestamps and safe failure classification. Private source content or Storage locations are not included by default.
- Keep the current active generation searchable while a replacement version is uploading, queued, processing, retrying or failed. Activation of a ready replacement follows the owner-approved policy and remains an atomic PostgreSQL decision.
- Make ingestion recovery states actionable: distinguish transient retryable failures, permanent input failures, exhausted retries, abandoned/expired leases, projection drift and cleanup/reconciliation work.
- Reuse existing jobs, attempts, leases, fencing and reconciliation mechanisms. Add only the narrow commands needed to retry a retryable job, rebuild the derived projection for an immutable version, or safely resume/requeue work whose ownership has expired.
- Ensure every recovery command is idempotent or rejects conflicting active work, records actor/reason where an operator initiated it, and never edits immutable source content.
- Add a bounded authenticated retrieval diagnostic that uses the same server-authorized Knowledge scope, embedding profile, Qdrant filters and PostgreSQL revalidation as runtime retrieval.
- Let diagnostics target either explicitly selected Knowledge bases or an Agent's resolved Knowledge assignment according to the approved permission model. Public Agent IDs and caller-supplied base IDs identify candidates but never grant access.
- Return interpretable diagnostic facts: resolved target/scope, active source versions/generations considered, final ranked validated hits, safe score/distance data where meaningful, source locator, and aggregate reasons for zero or discarded results. Do not expose another tenant's hit, an unvalidated Qdrant payload or internal provider credentials.
- Make zero-result and degraded states explicit, including no assigned sources, no active ready generation, unavailable embedding/vector dependency, filtered stale points and no hit above the configured retrieval boundary.
- Show focused Knowledge UI states for freshness, version history, ingestion/recovery and diagnostic results, including loading, empty, partial, stale, failed, forbidden and dependency-unavailable states.
- Add operational signals for repeated terminal ingestion failure, lease recovery and projection cleanup backlog using bounded structured metadata rather than raw document text.
- Update only authoritative Knowledge and cross-cutting documentation whose implemented behavior changes.

## Non-goals

- Controlled URL sources, scheduled remote synchronization, unrestricted crawling, arbitrary URL fetching or a browser/search tool.
- Automatic claims that a source is factually correct, complete, conflict-free or safe because it is recently reviewed.
- Automatically disabling, deleting or replacing active Knowledge solely because a review date elapsed.
- In-place editing of source versions, continuously self-editing Knowledge or automatic content rewriting.
- Semantic document diffing, AI-generated conflict resolution, prompt optimization or automatic remediation.
- A model completion, answer-quality evaluation, feedback queue or rollout decision; those belong to the Agent runtime and phase 6.1 boundaries.
- A universal observability platform, generic job framework, workflow engine, plugin registry or provider experimentation surface.
- Changing Catalog/Commerce structured truth, effectful tools, orders, payments, refunds, stock or channel providers.
- Persisting every diagnostic query or full retrieved content as a new analytics/event warehouse.

## Confirmed Decisions

- Freshness is explicit review provenance over an immutable source version. It is distinct from ingestion success, retrieval availability and factual correctness.
- Current manual/file inputs are the only source types in this phase. A new remote source type requires a separate trust, fetch, synchronization, size, retention and failure policy.
- Source replacement creates a new immutable version. Historical versions remain attributable and are never rewritten to simulate an update.
- The last good active generation remains searchable until a complete ready replacement is explicitly selected by the approved activation policy.
- PostgreSQL activation and authorization decide what is searchable. Qdrant state, similarity score and diagnostic output cannot activate, revoke or authorize a source.
- Recovery extends the existing ingestion state machine, leases, fencing and reconciliation behavior rather than introducing a second worker/job system.
- Retrying or rebuilding derived work never changes source content and cannot bypass current file validation, quotas, embedding-profile compatibility or tenant scope.
- Retrieval diagnostics reuse production retrieval authorization and validation but do not call the chat model, create a Conversation, publish an Agent or mutate channel bindings.
- Diagnostics explain observable pipeline facts; they do not present a provider-specific similarity score as a universal quality grade.
- Normal logs, metrics and audit metadata exclude query text, chunk content, uploaded text, signed URLs, secrets and raw provider payloads.

## Schema Impact

An additive migration is expected for version-aware freshness/review metadata and operator attribution. The final shape may store review facts on document versions with a document-level policy or due-time projection, but it must preserve immutable version provenance and avoid copying source content.

Existing document-version, generation, active-generation, ingestion-job, ingestion-attempt, embedding-mapping and media-asset records should be reused for history and recovery. Additive actor/reason fields or a narrow recovery audit record may be required if existing attempt evidence cannot attribute an operator action without conflating it with worker execution.

Retrieval diagnostics are request-scoped by default and are not expected to require a trace table. Any proposal to retain diagnostic queries, snippets or full result payloads requires separate owner approval of purpose, access and retention.

Every tenant-owned relationship must preserve workspace consistency. Indexes must support bounded document/version history, freshness filtering and job/recovery lookup without introducing queries over all tenant content. No existing source, generation or job table is renamed or repurposed.

## API Impact

Additive authenticated dashboard contracts are expected for:

- reading and updating approved source-review/freshness metadata;
- creating a replacement manual/file version with idempotency and existing upload limits;
- listing bounded version/generation/ingestion history;
- retrying or rebuilding eligible ingestion work and reporting conflicts explicitly; and
- executing a bounded retrieval diagnostic against selected Knowledge bases or an authorized Agent target.

Responses must distinguish document, version, generation and job state rather than collapsing them into one ambiguous status. Mutation responses must state whether the active searchable generation changed. Lists use stable bounded pagination, and retry/rebuild requests use idempotency or state preconditions where duplicate submission can create work.

Diagnostics accept bounded query text and result limits. Results identify only authorized resources and include stable reason codes for exclusions/failures alongside localized display copy in the client. Dependency failure, no eligible source and no matching hit remain distinct outcomes.

Existing Knowledge routes and response fields remain compatible. No public/widget diagnostic or recovery endpoint is introduced.

## Frontend Impact

Extend the current Knowledge management workflow rather than replace application navigation. Operators should be able to distinguish:

- source freshness from ingestion health;
- latest uploaded version from active searchable version;
- a failed candidate version from the still-serving last good version; and
- retryable failure from replacement-required or operator-forbidden recovery.

Version history and recovery actions should use progressive disclosure so routine source management remains compact. Destructive or potentially costly rebuild actions require clear target/version identity, confirmation consistent with current UI conventions and visible in-progress/conflict outcomes.

The diagnostics surface must show the selected scope, query, active versions considered, validated result order and zero-result explanations. Private snippets are displayed only to a role permitted to read source content, are rendered as untrusted plain text, and have an accessible structured alternative to any score visualization. Color is never the sole indicator of freshness, failure or rank.

The UI includes loading, empty, partial, stale, processing, failed, forbidden, conflict and provider-unavailable states and remains usable without Commerce data.

## Security Impact

- Every freshness, version, recovery and diagnostic request authenticates the dashboard actor, resolves current workspace membership and scopes all records on the server.
- Source IDs, version IDs, job IDs, Agent public IDs and Qdrant point IDs never grant access. Cross-workspace existence remains hidden according to current API conventions.
- Replacement text/files and diagnostic queries are untrusted input. Existing type, size, parsing isolation, prompt-injection, quota and private Storage controls continue to apply.
- Diagnostic scope is derived from authorized Knowledge bases or the server-resolved Agent assignment. The client cannot widen allowed sources, select an embedding profile or skip PostgreSQL revalidation.
- Returned snippets and locators come only from validated active chunks and are safely rendered. Raw Qdrant payloads, private object keys/URLs, stack traces and provider error bodies are never exposed.
- Retry/rebuild/resume operations require approved write/recovery authority, reject active conflicting leases, preserve fencing and cannot resurrect deleted/revoked documents.
- Operator actions retain safe attribution and timestamps. Logs and metrics use IDs, reason codes, counts and latency rather than source/query/chunk content.
- Retention and deletion revoke PostgreSQL access first; historical UI and diagnostics must not restore access to expired source content or derived vectors.

## Test Plan

- Migration rehearsal covers upgrade, constraints, indexes, representative current documents with no freshness metadata, and practical downgrade/rollback.
- Tenant tests use two workspaces with similar base, document, version, generation, job and Agent identifiers and deny every cross-workspace read, replace, review, recover and diagnostic path.
- Freshness tests cover unknown/default state, reviewer attribution, due-boundary calculation with timezone-safe timestamps, invalid cadence/dates, stale display and the guarantee that overdue status alone does not revoke retrieval.
- Version tests cover immutable manual and file replacements, monotonic version numbers under concurrency, duplicate-content handling, upload/storage failure and history pagination.
- Activation tests prove the old ready generation remains active during candidate upload/processing/failure and that only one complete ready generation is selected atomically under the approved activation policy.
- Recovery tests cover retryable and permanent failures, exhausted attempts, duplicate retry/rebuild requests, active-job conflicts, expired lease recovery, fencing of late workers, deleted/revoked documents and projection cleanup/rebuild.
- Retrieval diagnostics tests prove server-derived scope, production-equivalent filters, active-generation selection, PostgreSQL revalidation, stable bounded output and explicit no-source/no-hit/dependency-failure states.
- Adversarial diagnostics tests cover prompt-like query/source text, forged base/Agent/version/job IDs, stale or tampered Qdrant payloads, oversized queries, forbidden roles and response/log redaction.
- Permanent scenarios cover a Knowledge-only Agent with no Commerce records and a Commerce-enabled Agent whose structured Catalog facts remain outside Knowledge diagnostics.
- Frontend tests cover freshness labels, latest-versus-active version clarity, recovery eligibility, action conflicts, accessible diagnostic results and loading/empty/partial/error/forbidden states.
- Automated tests use fake embedding/vector providers and never incur paid calls. Documentation verification includes link/status consistency and `git diff --check`.

## Acceptance Criteria

- An authorized operator can see the active searchable version separately from the latest candidate version and can inspect bounded immutable history without exposing private Storage details.
- Each current source has explicit review provenance and a comprehensible freshness state; unknown or overdue freshness is visible but does not silently revoke a valid active generation.
- Replacing manual text or a supported private file creates a new immutable version and preserves creator, time, content identity and prior version history.
- The last good active generation remains searchable throughout candidate upload, ingestion, retry and failure; a new version becomes active only as a complete ready generation under the approved policy.
- Retryable, terminal, lease-expired and projection-drift states are distinguishable, and authorized recovery is bounded, attributable, conflict-safe and idempotent where duplicate work is possible.
- An authorized operator can run a bounded diagnostic that uses the same Knowledge scope, filters and PostgreSQL revalidation as runtime retrieval and clearly explains returned hits or a zero-result/degraded outcome.
- Diagnostics cannot widen Agent/base scope, expose unvalidated Qdrant data, call the chat model, create conversation state or change publication/bindings.
- Tenant denial, role enforcement, upload/query limits, redaction, retention, fencing and fake-provider coverage pass for every new surface.
- Existing Knowledge-only, Commerce, published-revision, channel, quota, cleanup and source-reference behavior remains compatible.
- No crawler, remote sync, self-editing Knowledge, opaque quality score, generic job/observability framework or effectful domain action is introduced.

## Approved Owner Decisions

The owner approved the conservative first slice on 2026-10-16:

- Version history, freshness review, replacement, recovery and diagnostics are owner/admin-only; workspace members retain existing read access to the compact Knowledge list metadata.
- Freshness uses an optional per-version next-review time with a fixed seven-day due-soon window. Reviewer notes are not retained.
- A ready candidate generation cuts over automatically and atomically; the previous active generation remains searchable until then.
- Version comparison is metadata/status-only. No source body, binary diff or semantic diff is returned.
- Dashboard recovery supports attributable retry and immutable-version rebuild with a required reason and confirmation in the UI. Expired leases continue through the existing fenced worker recovery path.
- Diagnostics support selected Knowledge bases and server-resolved Agent assignments. Owner/admin users may see snippets bounded to 500 characters from PostgreSQL-revalidated active chunks.
- Diagnostic requests and results are ephemeral. Logs retain only normal route metadata and never query or chunk content.
- Automated verification uses fake providers only. No live-provider diagnostic or rebuild was approved.
