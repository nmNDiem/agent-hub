# M2.1 — General-purpose Agent baseline

Status: **Implemented — approved 2026-10-16**

## Goal

Prove the existing Agent, Knowledge, publication and Website conversation path works without Commerce records, while preserving current Commerce behavior and compatibility.

## User-visible outcome

A workspace can configure, ground, publish and operate a knowledge-only Agent without products, locations, inventory or Commerce setup. Commerce-enabled Agents continue to provide validated product behavior.

## Existing Behavior to Preserve

- Existing published revisions and public identifiers remain usable.
- Commerce Agents retain catalog scope, validated product evidence and current channel behavior.
- Knowledge retrieval remains PostgreSQL-authoritative with Qdrant as a derived index.
- Website origin/session isolation, usage quotas, retention and tenant denial remain intact.
- No route or schema rename is performed for terminology alone.

## Scope

- Audit Commerce-specific defaults and fixed runtime composition in the Agent, publication and Website paths.
- Make knowledge-only behavior explicit where current coupling prevents or misrepresents it.
- Exclude Catalog tools and product rendering when no authorized Catalog capability/scope applies.
- Add permanent regression coverage for knowledge-only and Commerce-enabled scenarios.
- Update only the authoritative domain/cross-cutting docs whose behavior actually changes.

## Non-goals

- Generic capability/plugin registry or workflow engine.
- Effectful tools, orders, payments or stock mutation.
- New provider/channel implementation.
- Broad navigation redesign or World UI implementation.
- Repository-wide renames of `chatbot`, `shop` or existing routes.

## Confirmed Decisions

- Agent and Workspace remain generic.
- Runtime composition is server-owned and may expose only authorized concrete tools.
- Structured Commerce facts remain outside Knowledge/RAG.
- The smallest compatible change is preferred over a new universal abstraction.

## Schema Impact

None expected. Any discovered need requires owner review before implementation continues.

## API Impact

Additive or no change expected. Existing clients remain compatible.

## Frontend Impact

Only labels/states necessary for a coherent knowledge-only flow; no broad information-architecture change.

## Security Impact

No new side effects. Existing tenant, session, retrieval and evidence validation remain mandatory.

## Test Plan

- Backend regression proving publish/runtime with Knowledge and no Catalog records.
- Runtime test proving Catalog tools are unavailable when not authorized/applicable.
- Existing Commerce runtime/evidence tests remain green.
- Website/widget scenario covers grounded response without product cards.
- Negative cross-workspace Knowledge and session tests remain green.
- Focused frontend tests only for user-visible behavior changed by the phase.

## Documentation Impact

Update Agents/Knowledge packets and current API/UI references only if executable behavior changes. Do not broaden roadmap or future-domain documentation during implementation.

## Acceptance Criteria

- A workspace with no Commerce records can configure, publish and use a Knowledge-grounded Website Agent.
- The knowledge-only runtime does not load sales-only instructions, Catalog tools or product cards.
- A Commerce-enabled Agent preserves existing Catalog scope and validated product evidence.
- Published-revision, tenant-isolation, quota and retention behavior remain compatible.
- No speculative registry/framework, effectful action, schema rename or unrelated UI refactor is introduced.
- Verification commands and results are reported accurately, with no paid provider calls.

## Blocking Owner Decisions

Approved on 2026-10-16. No additional product decision was required; implementation introduced no schema or public-contract change.
