# 4.1 — Qualified contact and structured intake

Status: **Proposed — not approved for implementation**

## Goal

Let an authorized published Agent collect a small, operator-defined set of information for one concrete contact or service-request intake, validate it against an immutable server-owned definition, and persist one attributable submission in the existing Contacts/Leads domain without turning prompts, conversation text or model output into authoritative structured state.

## User-visible outcome

A workspace owner or admin can configure what an Agent needs to ask for a contact or service request, explain the purpose to the customer, and publish that definition with the Agent. In an eligible Website, Facebook Messenger or Zalo conversation, the Agent asks only for missing required information, summarizes the proposed request for correction, and records it once after the customer clearly accepts it.

The customer answers in ordinary language and never has to see field keys, schemas or a disguised step-by-step form. The Agent interprets one reply into every supported field it can justify, carries context forward, and asks a natural follow-up only for information that is missing or genuinely ambiguous. It communicates with the fluency, context awareness and initiative expected of a capable staff member, but never falsely claims to be human and identifies itself accurately when asked or when disclosure is required.

The resulting Lead remains in the existing Lead, Contact and Conversation workflows. Authorized operators can see the submitted fields, definition version, source Conversation, Agent revision, completion state and a separate human-owned qualification decision. The Agent may report that the request was recorded, but it cannot decide that the person is qualified, promise acceptance or response time, or initiate delivery outside the current conversation.

## Existing Behavior to Preserve

- Contacts remain workspace-level communication identities; Leads remain consented follow-up events/state and do not become Commerce Customers.
- `contacts.follow_up.request` remains a distinct, working action with its current Website contact-method rule, verified Facebook/Zalo identity rule, one-Lead-per-Conversation behavior, live revocation, idempotency and retention contract.
- Website callback capture remains a separate explicit-consent form and keeps its current public API and session ownership rules.
- Agent permissions are opt-in, snapshotted into immutable revisions and rechecked against live state. Playground has no effectful tools.
- Website, Facebook and Zalo share normalized Conversation and Contact behavior while provider identity, response windows, opt-out and connection health remain server-owned.
- AI/human handling mode, takeover, assignment, Contact visibility, Lead status, Contact merge/reversal and CSV-safety behavior remain intact.
- PostgreSQL is authoritative. Conversation text may inform a proposed tool call but is not a structured intake record; model output, prompts, provider payloads and Qdrant never become authoritative answers.
- Action evidence remains narrow and redacted. It cannot duplicate submitted answers, contact values, messages, prompts, provider identities or raw tool arguments.
- Existing Knowledge-only and Commerce-enabled Agent read behavior remains compatible and independent of whether structured intake is configured.

## Scope

- Add one optional structured-intake configuration to an Agent draft. The first slice supports one published intake definition per Agent revision, one purpose and at most twelve ordered fields; it is not a reusable workspace-wide form catalog.
- Give every field a stable server-generated key, operator-visible label, optional help text, required flag and one bounded type: short text, long text, email, phone, single choice, multiple choice or date. Choice fields use stable option keys and bounded operator-authored labels.
- Bound labels, help text, option counts, answer lengths and total serialized definition/answer size. Reject duplicate keys, empty required choices, invalid defaults, unsupported types and extra properties at the API boundary.
- Allow owners/admins to configure only the approved low-risk intake categories: identity/contact details, service category, general location or service area, preferred date, preferences and bounded free-text context. Product copy and validation must prohibit passwords, authentication secrets, payment-card or bank data, government identifiers, precise geolocation, health/biometric data and other sensitive-category collection.
- Snapshot the full validated intake definition, purpose/disclosure version and enablement into the immutable Agent revision. Editing the draft has no effect on a published conversation until a new revision is published; live disable still fails closed immediately.
- Introduce one Contacts-owned typed action, `contacts.intake.submit`, available only in eligible real conversations whose active revision contains an enabled intake definition. Do not expose the action in Playground or through a public arbitrary-tool endpoint.
- Bind workspace, Agent, revision, intake definition, Conversation, current inbound source message, Channel connection, Contact identity and actor on the server. Tool input contains only stable field keys and proposed typed values; it cannot select ownership, permission, retention, qualification, Lead state or provenance.
- Compose the published purpose, field labels, allowed choices and missing-field guidance into bounded server-owned runtime instructions. Operator instructions and retrieved content cannot add fields, alter validation or authorize submission.
- Let the Agent collect answers conversationally through normal messages. Customers respond in ordinary language rather than field syntax, JSON, a mandatory sequence or a form presented one question at a time. The runtime may propose values for multiple configured fields from one customer reply when each value is supported by that reply and bounded conversation context.
- Carry already supplied information forward and ask only for a required value that remains missing or for a value whose ambiguity prevents safe validation. Follow-up wording uses the Agent's approved locale and personality instead of exposing internal field names or repeating a rigid questionnaire. If the ambiguity cannot be resolved naturally, leave the intake unsubmitted and preserve normal human handover.
- The first slice does not persist partial structured drafts; until final submission, customer input remains only in the existing Conversation under its current retention and access policy.
- Before submission, present a concise natural-language summary of the proposed intake and invite correction without reciting a technical field list. Submit only after an explicit customer request or clear acceptance in the current bounded conversation. Silence, browsing, inferred intent, an Agent-authored suggestion or an operator prompt cannot authorize submission.
- Validate the complete payload again in the Contacts service against the immutable published definition. Normalize email/phone through current Contact rules, validate dates without inventing timezone semantics, accept only configured choice keys, and return stable missing/invalid field keys without echoing customer values.
- Atomically create or reuse the Conversation's Lead, persist one finalized intake submission and record narrow action execution evidence. Website still requires a validated customer-supplied email or phone; Facebook/Zalo still use the verified server-resolved provider Contact identity.
- Keep one finalized intake submission per Conversation in the first slice. An identical normalized replay returns the existing result; a conflicting replay or post-submission correction fails explicitly and leaves the original authoritative submission unchanged for human review.
- Record submission completeness as a server-derived fact. All configured required fields must be present and valid before a finalized submission can be stored.
- Add a human-owned Lead qualification state separate from follow-up workflow: `pending_review`, `qualified` or `not_qualified`. New intake Leads start at `pending_review`; only an authorized dashboard operator can change it. The Agent, model and intake answers cannot assign or infer this state.
- Show the finalized intake and human qualification state in existing Lead/Contact/Conversation workflows with field-level PII authorization. The conversation projection contains only a safe submission summary, not all answers by default.
- Retain submitted answers for the same approved contact-request purpose and no longer than the Lead/Conversation boundary. Deletion or expiry removes answer values and sensitive references before any content-free execution fact that may remain.
- Add bounded operational metrics for attempted, completed, replayed, validation-needed, denied and failed submissions using safe identifiers, field counts and codes only.
- Update only authoritative Agent, Contact/Lead, Conversation, API, data-model, security, testing, operations and UI documentation whose implemented contracts change.

## Non-goals

- A generic Forms product, drag-and-drop form builder, custom-object platform, reusable questionnaire library, workflow engine, rules engine or capability registry.
- More than one intake definition per Agent revision, branching/conditional questions, calculated fields, cross-field formulas, repeating groups, file uploads, signatures, arbitrary JSON fields or operator-authored validation code.
- A model-generated intake schema, model-selected retention policy or prompt-defined database field.
- A customer-facing form disguised as chat, a rigid one-field-per-turn questionnaire, requests for JSON/field keys or repeated questions for information the customer already supplied.
- Falsely claiming that an automated Agent is a human employee, inventing a human identity or evading a direct question about automation. Natural staff-quality communication does not authorize deceptive identity claims.
- AI lead scoring, sentiment scoring, demographic inference, automatic qualification/disqualification, profiling, marketing segmentation or automated decision-making.
- Persisted partial intake drafts, cross-conversation intake continuation, anonymous pre-chat forms or a separate customer portal.
- Automatic mutation of a finalized submission. Corrections after submission remain visible in Conversation and require human handling in this slice.
- Replacing Contact notes, tags, assignment, Lead follow-up status, Contact merge or human handover.
- Proactive messaging, campaigns, document/email delivery, appointment booking, external webhooks, arbitrary API calls or any Commerce mutation.
- Collecting credentials, payment data, government identifiers, health/biometric data, precise location or other sensitive-category information.
- Native Facebook/Zalo interactive forms or buttons. Normalized text remains the complete functional path.
- A workspace-wide action console, generic execution ledger, general approval framework or arbitrary retry endpoint.
- Reporting, filtering or analytics over arbitrary intake-answer values beyond viewing one authorized submission and safe aggregate action counts.

## Confirmed Decisions

- Structured intake extends the existing Contacts/Leads aggregate and the proven effectful-action boundary; it does not create a peer Forms domain.
- The action contract is definition-driven but remains concrete and Contacts-owned. A bounded schema for this workflow is not a generic action or plugin schema.
- Definitions are immutable at execution time through the published Agent revision. Draft edits cannot reinterpret an existing submission or alter a running revision.
- A stable field key and definition snapshot give historical answers meaning. Operator labels may change only in a later draft/revision and do not rewrite historical submissions.
- Conversation text helps the Agent ask questions but is not treated as validated structured state. Only a successful Contacts transaction creates the finalized submission.
- The structured definition is an operator/backend contract, not the customer interaction model. The Agent interprets free-form conversation into a typed proposal, may fill several fields from one supported reply, and asks naturally only for missing or materially ambiguous information.
- Staff-quality conversation means fluent, contextual and proactive assistance without robotic form behavior. It does not mean impersonating a human; the Agent answers identity questions truthfully and follows any applicable disclosure requirement.
- Qualification is an accountable human decision separate from required-field completeness and follow-up status. The model cannot derive it from answers.
- The first slice stores no partial structured draft. This keeps recovery, amendment and retention behavior narrow while preserving ordinary Conversation history and handover.
- A submitted intake is immutable in the first slice. Compatible retries replay; conflicting data fails closed instead of silently overwriting customer-provided information.
- Website reachability and social-provider reachability retain the rules already proven by `contacts.follow_up.request`; no client or model may fabricate identity evidence.
- The intake creates internal state only. It does not send an external request, guarantee service eligibility, promise a response or invoke downstream workflows.
- Sensitive categories are outside the approved first slice. A later need must define purpose, access, retention, legal basis and additional safeguards in its own approved packet.
- One PostgreSQL transaction is sufficient because the workflow has no external side effect. Provider reconciliation, saga machinery and a generic job system would be speculative.

## Schema Impact

Additive Alembic migrations are expected.

The Agent draft needs an optional bounded structured-intake definition and enablement state. Each immutable Agent revision needs a complete validated snapshot with stable field/option keys and purpose/disclosure version. The implementation may use validated JSON for this small revision-owned configuration if it enforces an explicit schema and size limits; it must not become an untyped arbitrary configuration bag.

Add a narrow Contacts-owned finalized intake submission linked workspace-consistently to Contact, Lead, Conversation, Agent and Agent revision. It must retain the immutable definition identity/hash or snapshot needed to interpret historical stable field keys, a normalized payload hash, completion state, timestamps and retention boundary. Answer storage may use bounded typed JSON or normalized rows, but database/application constraints must prevent unknown fields, unsupported value shapes and tenant-inconsistent references. No answer value is copied into execution evidence.

Extend the Lead with a checked human qualification state or an equivalently narrow Contacts-owned record. Follow-up status remains independent. Qualification changes require actor attribution, optimistic concurrency or an equivalent lost-update guard, timestamp and an optional bounded non-sensitive reason; they do not rewrite the submission.

Add action-specific execution evidence for `contacts.intake.submit`, following the redaction and transaction guarantees of the existing follow-up action. Reuse proven internal helpers where appropriate, but do not broaden the current follow-up table into a speculative global action ledger. The execution record supports server-generated idempotency, normalized request-hash comparison, safe states/codes, replay count, timing and retention cleanup.

Indexes must support workspace-scoped Lead/Contact/Conversation lookup, replay detection, operator qualification queues and retention cleanup without querying arbitrary answer content or crossing tenants. Uniqueness enforces at most one finalized intake per Conversation for this slice. Existing Leads, follow-up executions, Agent revisions and Website form submissions backfill to no intake and preserve behavior.

No migration may make model output, prompt text, provider payloads or Qdrant authoritative. Generate migrations through Alembic and follow current migration conventions rather than manually editing generated artifacts outside those conventions.

## API Impact

Extend authenticated Agent draft/read/update/publish DTOs with one strict structured-intake configuration. Extra properties remain forbidden. The API returns stable field/option keys, validates all limits and exposes whether the current published revision differs from the draft. Existing Agents and revisions default to intake disabled.

Extend authorized Lead detail and Contact timeline contracts with the minimum submission metadata and answer values permitted to that role. List rows and Conversation projections expose only safe facts such as purpose label, completeness, definition/revision reference, submission time and qualification state. They do not expose all free-text answers, internal hashes, raw source messages or provider identity.

Add or extend a focused authenticated Lead mutation for human qualification state. It uses current workspace membership and Contact/Lead visibility, requires CSRF protection, rejects stale versions, records actor/reason safely and cannot mutate intake answers or follow-up status implicitly.

No public intake-submission endpoint and no generic action endpoint are added. The eligible published runtime invokes `contacts.intake.submit` internally after server-side context resolution. Website callback routes and `contacts.follow_up.request` remain compatible.

Stable errors distinguish disabled/unpublished intake, stale definition or source message, missing/invalid required fields, unsupported value, missing Website reachability, unavailable social identity, compatible replay, idempotency conflict, finalized-submission conflict, human-takeover fence, expired/revoked context, forbidden qualification change and retryable internal failure. Cross-workspace and cross-conversation references follow existing non-disclosure conventions.

## Frontend Impact

Add a focused structured-intake section to the existing Agent configuration flow or an approved contextual subview. Do not add Forms to top-level navigation or expose internal tool/action schemas. Because this introduces material configuration UI, implementation requires owner-approved UI direction before code changes begin.

The editor shows purpose/disclosure, enablement, ordered fields, type, required state and bounded choices. It provides accessible validation, field-count/length limits, draft-versus-published state and clear warnings that sensitive data, credentials and payment details are prohibited. Reordering and editing remain keyboard accessible; color is not the only state indicator.

The customer experience stays in normal Website/Facebook/Zalo conversation text. The Agent understands ordinary replies, extracts every justified configured value from the same message, remembers values already supplied, asks only about missing or materially ambiguous information, explains why it is needed, accepts correction before submission and shows a concise summary for explicit acceptance. It never exposes field keys, asks for JSON or turns the chat into a rigid one-question-per-field form. No forced provider-specific form or new pre-chat gate is required.

Copy should feel like a capable staff conversation: fluent, contextual and appropriately proactive rather than repetitive or mechanical. The Agent does not repeatedly announce that it is automated, but it must not claim or imply a fabricated human identity and must answer accurately when the customer asks who or what they are speaking with.

Existing Lead and Contact detail surfaces show the finalized definition label, submitted fields according to role, source Conversation, Agent/revision, completion and qualification state. Inbox/Conversation shows a compact safe card or timeline item that links to authorized detail rather than duplicating all answers.

UI states cover disabled, unpublished changes, unavailable in Playground, incomplete configuration, missing/invalid customer field, awaiting acceptance, recorded, replayed, conflict/correction-needed, forbidden, expired context, human takeover and safe failure. Customer-facing copy never claims qualification, acceptance, staffed availability or an SLA.

## Security Impact

- Every execution derives workspace, Agent, immutable revision/definition, Conversation, current inbound source message, Contact, Channel connection, actor and retention context on the server. Tool input cannot widen them.
- The action is absent unless both the live Agent and active published revision permit it. Disable, pause, archive, human takeover, revoked binding/connection, provider opt-out/window expiry and expired Website session fail closed.
- Only a current authenticated/scoped inbound visitor message may supply acceptance evidence. Guessed IDs, assistant-authored messages, quoted instructions, old messages and another Conversation's messages are denied.
- Definition configuration is owner/admin-only, strict and size-bounded. Labels/help text are untrusted and cannot alter platform policy or inject new tools/fields.
- Answers are untrusted PII-bearing input. Server validation enforces field membership, type, length, allowed choices, email/phone rules and total size independently of model validation.
- Model output cannot establish consent, identity, required-field completeness, qualification, permission or retention. It may propose a typed payload only after the customer has supplied and accepted the values.
- Submitted answers use current Contact/Lead role restrictions and purpose-limited retention. List projections, metrics, logs and execution evidence exclude answer values and free text.
- Passwords, authentication secrets, financial/payment credentials, government identifiers, health/biometric data, precise location and other sensitive categories are prohibited by contract and configuration guidance. Any later category requires a separate privacy/security decision and enforcement design.
- Normalized request hashing must use a deterministic canonical form without logging the canonical values. Hashes are not treated as anonymized public data.
- Compatible replay is idempotent, conflicting replay fails explicitly, concurrency cannot create two finalized submissions and rollback cannot leave successful evidence without the Lead/submission.
- Retention cleanup removes answer values and sensitive references before deleting owning Contact/Lead/Conversation state. Historical definition metadata cannot reconstruct expired answers.
- Qualification mutations are authenticated, role-authorized, tenant-scoped and attributed. They cannot be triggered by the model, customer channel or intake action.

## Acceptance Criteria

- An owner/admin can configure one bounded structured intake for an Agent, publish its immutable definition and disable it fail-closed; unauthorized roles and old/disabled revisions cannot execute it.
- The definition supports only the approved field types and limits, rejects unknown/invalid configuration and cannot request prohibited sensitive categories under the approved product contract.
- In an eligible real Website, Facebook or Zalo conversation, the Agent asks only for missing required values, presents a concise correction opportunity and submits only after explicit customer request or acceptance.
- Customers can answer in ordinary language. The Agent maps one supported reply to multiple configured fields, carries known values forward and never requires field syntax, JSON or a rigid form-like sequence.
- Customer-facing wording is fluent, contextual and proactive like capable staff assistance. The Agent does not falsely claim to be human, invent a human identity or evade a direct identity question, and unresolved ambiguity can fall back to normal human handover without storing an incomplete intake.
- The Contacts service validates the complete payload against the immutable published definition and server-bound workspace, Agent/revision, Conversation, current inbound message, Contact and Channel context.
- Website submission requires validated customer-supplied email or phone; Facebook/Zalo use only the verified server-resolved provider identity and never fabricate Website or contact data.
- One atomic transaction creates or reuses the Conversation's Lead, stores one complete immutable intake submission and records redacted action evidence. No partial structured state remains after rollback.
- Compatible duplicate calls replay one result; conflicting payloads and post-finalization corrections fail explicitly without overwriting the authoritative submission or creating another Lead.
- New intake Leads begin `pending_review`. Only an authorized human operator can mark them `qualified` or `not_qualified`; required-field completeness and model output cannot do so.
- Authorized operators can view the submitted fields and provenance in existing Lead/Contact workflows, while Conversation/list projections, logs, metrics and execution evidence remain minimal and redacted.
- Submitted answer values expire with the approved Lead/Conversation purpose boundary and cannot be reconstructed from retained evidence, hashes or definition metadata.
- Existing Website callback capture, `contacts.follow_up.request`, Lead follow-up status, Contacts, Inbox/handover, Agent publication, Channel policy, Knowledge-only behavior and Commerce read tools remain compatible.
- Tenant denial, role enforcement, source-message evidence, human-takeover fencing, validation, idempotency, concurrency, rollback, retention and fake-provider coverage pass for every new surface.
- No generic Forms domain, workflow/rules engine, AI scoring, arbitrary field/code execution, sensitive-data intake, provider-specific form dependency, proactive delivery or unrelated domain mutation is introduced.

## Blocking Owner Decisions

Approval of this packet confirms all of the following product and release decisions:

- The first slice provides one intake definition per Agent revision, one finalized submission per Conversation and at most twelve fields. It does not provide reusable forms, branching or multiple request types.
- Supported fields are short text, long text, email, phone, single choice, multiple choice and date. File upload, signature, numeric formulas, repeating groups and arbitrary JSON are deferred.
- Operators may configure only low-risk contact/service-request data. Credentials, payment/financial data, government IDs, precise location, health/biometric data and other sensitive categories are prohibited rather than merely hidden.
- Customer acceptance uses a conversational summary and clear affirmative response; no separate checkbox is required for this low-risk internal record. Website callback form consent remains a separate flow.
- The structured definition remains invisible to customers. They answer naturally; the Agent may fill several fields from one reply and asks only for missing or materially ambiguous information rather than walking through a disguised form.
- The desired experience is staff-quality conversation, not human impersonation. The Agent need not repeatedly announce automation, but it must identify itself accurately when asked or when disclosure is required.
- Partial answers are not persisted as a structured draft. If the customer leaves before acceptance, only the existing Conversation remains and normal handover may continue.
- A finalized submission is immutable. Compatible retries replay; later corrections are handled by a person instead of silently overwriting the original in this slice.
- Qualification is a human-owned `pending_review | qualified | not_qualified` state separate from Lead follow-up status. The Agent never assigns it and no automatic score or eligibility rule is introduced.
- Website continues to require email or phone, while Facebook/Zalo may use their verified provider identity and Conversation without fabricating contact fields.
- Submitted answers share the approved contact-request purpose and current 30-day Lead default, bounded by the shorter owning Conversation/Lead retention. They are not reused for marketing or model training under this packet.
- Website, Facebook and Zalo normalized text are the complete first-slice channels. Native provider forms/buttons and a new widget form are deferred.
- UI direction for the Agent intake editor and operator detail state must be reviewed and approved before implementation because this packet introduces material configuration UI.
- A privacy/security review of purpose copy, allowed data categories, role access, export and retention is a production release gate. This packet is not legal advice.
