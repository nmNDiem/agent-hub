# ID strategy — UUIDv7 where necessary, BIGINT by default

## Distinction
A PostgreSQL `uuid` **column** accepts UUIDv7 **values**. There is no special SQL type named `uuidv7`. UUIDv7 is time-ordered but contains timestamp bits: do not treat identifiers as secrets or claim they hide creation time. Do not derive business chronology solely from ID; use `created_at` and a tie-breaker.

## Canonical mapping
| Table | PK | Public identifier | Notes |
|---|---|---|---|
| users | `uuid` **v7** | `id` | created server-side; independence from Supabase Auth |
| workspaces | `uuid` **v7** | `id` | exposed to admin API only after auth |
| workspace_members | `bigint` identity | none | composite unique workspace+user |
| agents | `bigint` identity | `public_id uuid UNIQUE` **v7** | embed and admin URLs |
| agent_revisions | `bigint` identity | none | immutable version number per bot |
| channels | `bigint` identity | none | future provider external ID string |
| conversations | `bigint` identity | `public_id uuid UNIQUE` **v7** | external route/public session lookup |
| messages | `bigint` identity | none | high volume; optional client idempotency key string |
| products / variants | `bigint` identity | none initially | SKU/workspace in business UI; add v7 only if external direct address is needed |
| knowledge_documents / chunks | `bigint` identity | none initially | private/admin only |
| media_assets / ingestion_jobs / audit_logs | `bigint` identity | none | access by workspace + domain relation |
| sessions | `bigint` identity | random opaque refresh token hash | bearer secrets **never UUIDv7** |

## Generation and storage
- Backend generates all UUIDv7 IDs before INSERT using a tested RFC 9562 implementation. On Python **3.14+**, stdlib `uuid.uuid7()` is available; if pinned lower, use a well-maintained UUIDv7 library with tests. Wrap in `new_uuid_v7()` and unit-test `UUID(value).version == 7` and uniqueness. Never silently replace with `uuid4()`.
- PG18 offers native `uuidv7()`; **do not require it** because Supabase project PG version varies. Migrations define `id uuid PRIMARY KEY` **without `gen_random_uuid()` defaults**; app supplies ID. Once runtime version is confirmed an ADR can move generation into database.
- `BIGINT GENERATED BY DEFAULT AS IDENTITY` (or ALWAYS with deliberate seed handling) for internal tables. All foreign key types must match the corresponding PK. Use `UNIQUE(workspace_id, sku)` where relevant, and unique scoped public IDs globally.
- API canonical external string: plain lower-case UUID with hyphens. Mockups' `bot_0198…` and `conv_0198…` are **visual sample labels**, not SQL UUID values or canonical API IDs; `Copy ID` copies raw UUIDv7. Do not manually paste mockup strings as fixtures.
- Server never exposes BIGINT IDs in public widget payloads or trusts client-provided internal IDs without checking tenant; an optional opaque alias may be added only by documented adapter.

## Indexing / performance
B-tree unique index on public_id; `(workspace_id, created_at DESC, id DESC)` on large tenant tables; `(conversation_id, id)` messages; tenant+vector strategy documented elsewhere. Time ordering of UUIDv7 may improve index locality compared to random v4 but is **not** a replacement for measuring performance.

## Correct code examples
```python
from uuid import UUID

def assert_uuid7(value: UUID) -> None:
    if value.version != 7:
        raise ValueError('Expected UUIDv7')

# Python 3.14+ only; otherwise use an audited package behind this adapter.
from uuid import uuid7
agent_public_id = uuid7()
```

```sql
CREATE TABLE example_agents (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  public_id uuid NOT NULL UNIQUE, -- application-generated v7
  created_at timestamptz NOT NULL DEFAULT now()
);
```
