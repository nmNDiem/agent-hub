# ADR F3.4 — Bounded grounded agent runtime

Status: Accepted (2026-09-30), amended (2026-10-03).

## Context

F3.1 provides immutable workspace/location/collection authorization and typed catalog
tools. F3.3 provides tenant-filtered knowledge retrieval with PostgreSQL revalidation.
F3.4 must compose those boundaries with OpenAI generation without allowing model text,
user prompts, or retrieved documents to become an authority for catalog facts, tenant
scope, tool permissions, or provider spending.

## Decision

- `ModelGateway` is provider-neutral and `OpenAIGenerationGateway` is the only concrete
  generation implementation. The exact model is operator-configured through
  `GENERATION_MODEL`; there is no guessed application default or shop-owner model selector.
  The local environment template selects the operator-verified `gpt-6-luna`. Because this
  adapter uses Chat Completions function tools, it sends `reasoning_effort="none"` only for
  that model and leaves other explicitly configured models on their native parameter set.
- The OpenAI adapter disables SDK retries, requires tool-call output, disables parallel
  tool calls, and records provider-reported token usage. Local Pydantic validation remains
  authoritative because supported models do not all implement the same strict JSON-schema
  subset.
- The runtime resolves one agent inside a validated workspace, then derives immutable
  catalog and knowledge scopes on the server. Model-visible tool schemas contain no
  workspace identifier. Catalog scope inputs may only narrow the resolved scope.
- Retrieval runs at most once per turn. Retrieved excerpts, agent style configuration,
  and the visitor question are serialized together as explicitly untrusted JSON beneath a
  fixed platform system policy. Retrieved instructions never become system or tool policy.
- The bounded loop permits only `search_products`, `get_product_detail`, `check_stock`,
  and `submit_grounded_answer`. It accepts one tool call per model turn and caps question,
  knowledge, prompt, tool-result, output-token, total-token, model-call, tool-call, and
  catalog-result sizes.
- The model emits a natural channel-neutral sales response and selects only product IDs already
  returned by an executed tool. It may explain exact commerce facts such as price, SKU, options,
  stock, discounts or links when those values are present in tool results, and may ask a helpful
  follow-up question. The server creates schema-neutral product cards from the same authoritative
  tool models.
  Cards preserve exact decimal price summaries, generic
  options/attributes, opaque image references, and explicit unknown inventory. Web and future
  social adapters render the same structured facts according to channel capabilities.
- Knowledge answers cite aliases for actually retrieved and revalidated chunks and may summarize
  or paraphrase them naturally. Grounding and prompt-injection resistance are instructed by the
  fixed platform prompt; output is not classified with locale-specific keyword lists. Unknown
  product/source references, tenant-scope arguments and malformed schemas remain objectively
  invalid. The runtime returns bounded protocol feedback so the model can repair recoverable
  calls; model-call, tool-call and token budgets still fail closed.
- Agent `safe_instructions` is applied as editable personality, tone, response-length and sales
  style guidance. It cannot change platform policy, tenant scope, tool permissions or evidence
  requirements. New agents receive locale-aware greeting and personality defaults when those
  fields are omitted, while explicit values remain authoritative.
- Runtime exceptions preserve stable internal codes and the original provider/tool exception as
  the Python cause. F3.5 logs only the redacted code and emits a neutral conversational fallback,
  not the code or a technical error banner. Prompts, credentials, private URLs and provider
  payloads are not returned or logged.
- F3.4 is an internal service boundary. It adds no browser/widget endpoint, conversation
  persistence, publish flow, or SSE transport; authenticated Playground delivery remains
  F3.5 and public widget delivery remains F4.

## Consequences

- Structured tools and cards remain authoritative for catalog data, while the model controls the
  natural wording and configured personality. Prompt-based claim grounding is less mechanically
  strict than keyword rejection or extractive-only knowledge answers, but avoids false positives
  across languages and supports conversational web and future social channels.
- Monetary cost is bounded indirectly by fixed request/model/tool/token limits. Dollar
  estimates remain model/deployment-specific and are not fabricated when pricing has not
  been configured.
- A retrieval outage can still permit authorized catalog use, but it cannot silently
  produce a cited policy answer. Provider and budget failures return a safe unavailable
  outcome for the future transport layer to map.
- F3.5 may stream the validated conversational message and structured server output through
  the documented SSE taxonomy, but it must not bypass final grounding validation by forwarding
  raw provider output.

## Verification

- Offline fake-gateway tests cover personality propagation, prompt injection boundaries,
  tenant-scope arguments, invalid product/source references, natural SKU/price/stock/discount
  prose, paraphrased cited knowledge, correction of malformed calls, generic options,
  product-only schemas, unknown inventory, provider redaction, conversational fallbacks and
  model/tool/token budgets.
- Adapter tests verify required sequential tool calls, bounded output, disabled storage,
  and provider token accounting without making a paid OpenAI request.
- A bounded live compatibility check confirmed that `gpt-6-luna` accepts the required
  Chat Completions function-tool request when `reasoning_effort="none"` is present.
- A tenant-negative service test proves that a public agent ID from another workspace is
  returned as a non-leaking `404` before any retrieval or model call.
