# ADR F3.2 — Durable knowledge ingestion and generation lifecycle

Status: Accepted (2026-09-29).

## Context

Knowledge ingestion accepts hostile files, makes paid external embedding calls and writes to both authoritative PostgreSQL state and a rebuildable vector index. API-process background tasks, unfenced leases or in-place document/profile mutation would allow lost work, stale-worker cutover, mixed vector spaces and partial generations to become visible.

## Decision

- PostgreSQL is authoritative for knowledge bases, immutable source versions, reproducible generations, chunk text, index mappings, jobs and attempts. Customer files remain private in Supabase Storage; Qdrant is derived state.
- The HTTP API streams and validates input, stores the immutable source and persists a job. It never performs PDF parsing or embedding inline. A separately deployed Python worker owns processing and reconciliation; Redis is not required for this workload.
- Jobs use `FOR UPDATE SKIP LOCKED`, one-active-job-per-document database uniqueness, per-workspace concurrency, expiring leases, heartbeat and a monotonically increasing fencing version plus random token. Every DB state transition and cutover checks the current fence.
- Document/base deletion wins races: it cancels active jobs and revokes active generations transactionally. Cutover locks and rechecks the job, document, base, generation, fence and indexed coverage before publishing.
- Source versions and processing generations are immutable. Each generation records the chunker version, chunk size/overlap, pipeline hash and embedding profile. A failed build never replaces the active generation.
- Embedding profiles are immutable configuration identities. Provider, model, dimensions, provider revision, pipeline version, metric, collection and config hash cannot be edited after creation. The platform operator/provider bootstrap creates profiles; workspace callers cannot supply model configuration.
- No guessed profile is seeded. Until F3.3 verifies the exact OpenAI model, dimensions and Qdrant collection, new jobs remain `awaiting_profile`. A future model change creates a new profile, assigns it as the knowledge-base target, produces new generations for every active source, verifies coverage/isolation, atomically promotes it and retains the prior profile/generations for controlled rollback until retention approval.
- Vector IDs are deterministic and upserts are idempotent. Payload includes workspace, knowledge base, document/version, generation, chunk, embedding profile and content hash. A reconciler deletes failed/revoked points and abandoned Storage objects.
- Automatic retry is limited to transient provider/storage/network failure. It uses five maximum attempts with exponential full jitter from 5 seconds to 15 minutes. Content, hash, format, dimension and quota errors are permanent.
- PDF extraction uses exact `pypdf==6.19.0`, strict mode and an isolated child process. The child is bounded by 30 wall seconds, 20 CPU seconds, 512 MiB address/process memory and 4 MiB output. Encrypted and image-only PDFs have explicit unsupported/no-text codes; OCR is not part of the MVP.
- Stable initial guardrails are code defaults: 10 MiB/source, 100 documents and 100 MiB source storage/workspace, 10 uploads/10 minutes, 200 PDF pages, 1,000,000 extracted characters, 1,200-character chunks with 150 overlap, 1,000 chunks/generation, 20,000 chunks/workspace, 64 embeddings/batch and two active jobs/workspace. Deployment may override intentionally.
- Logs contain identifiers and safe error codes only. They do not include source filenames as paths, file bytes, extracted/chunk text, provider payloads or tracebacks from hostile parsers.

## Authorization and identifiers

Knowledge IDs remain dense BIGINT values because they are authenticated dashboard resources, not public visitor handles. Every route first validates membership and scopes resource lookup by `workspace_id`; cross-workspace access is a non-leaking `404`, while a member lacking write permission receives `403`. Composite foreign keys prevent both cross-workspace links and same-workspace cross-document version/generation links.

## Consequences

- API replicas can scale independently from controlled worker replicas. Worker startup must be wired with concrete provider adapters and health/termination behavior in F3.3/deployment packaging; it must not be embedded as a FastAPI startup task.
- Storage or vector writes can precede a DB failure without corrupting authoritative visibility. Deterministic retry and reconciliation provide eventual cleanup, while Postgres active-generation checks prevent stale retrieval.
- F3.2 can be tested deterministically with fake external adapters. It is production-shaped but does not claim a functioning semantic search runtime before the separately gated OpenAI/Qdrant integration and retrieval validation.
- Malware scanning and final retention periods remain explicit production launch decisions. Parser isolation reduces impact but is not a malware scanner.

## Rejected alternatives

- FastAPI `BackgroundTasks` as the only runner: work is lost or duplicated across restarts/replicas.
- Lease expiry without fencing: an old worker can wake and overwrite a newer attempt.
- In-place embedding-model edits: existing vectors become incomparable or dimension-invalid.
- Treating Qdrant as authoritative: deletion, authorization, rollback and rebuild become weaker.
- Parsing PDFs in the API or worker process: crafted inputs can exhaust shared CPU or memory before application page/text counters run.

## Verification

Unit tests cover malformed/encrypted/historically pathological PDFs, hard wall timeout, transient retry, stale-worker fencing, deterministic indexing, all-or-nothing cutover and orphan cleanup. Opt-in PostgreSQL tests migrate an isolated schema and verify partial uniqueness, immutable profiles and composite document graph constraints.
